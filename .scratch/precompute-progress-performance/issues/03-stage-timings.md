# 03: 在进度日志中展示五段累计耗时

**What to build:** 用户在生成过程中能从进度日志辨认 Rust 提取、GRP 奖励推理、Python 样本整理、编码压缩和写盘提交各自花费的时间，从而定位瓶颈并比较运行参数。

**Blocked by:** 01 — 在 chunk 提交边界输出可配置的进度日志。

**Status:** ready-for-agent

- [x] 在现有进度触发点显示五段本次累计耗时：Rust/libriichi 提取、GRP 奖励推理、Python 样本整理、编码压缩、写盘与进度提交。
- [x] 计时围绕真实调用边界使用单调时钟，明确区分生成总开销及其子阶段，不能把包含 Rust/GRP 的总时间再次计为独立 Python 开销。
- [x] 编码时间包含固定布局编码与压缩，提交时间包含 chunk 与进度的保存；累计阶段耗时不强行解释为单个 chunk 的独占时间，也不要求五段合计覆盖全部 wall time。
- [x] 从恢复位置重新累计本次耗时，不把旧运行耗时或旧样本推算进统计；计时不会推动已提交游标或增加持久化字段。
- [x] 使用普通、轻量的模块实现整合计时，不把实验的动态源码替换或 monkey patch 接入生产流程，不增加后台采样器、统计数据库或新的产品入口。
- [x] 通过公开预计算入口捕获输出，配合受控计时或生成器边界验证阶段累计和恢复重置；断言业务含义，不为私有计时函数另建复杂测试接口。
- [x] 加入计时后，既有顺序生成、尾块、提交失败和恢复的外部结果不变；出现异常时不为输出统计而继续生成或报告成功。
