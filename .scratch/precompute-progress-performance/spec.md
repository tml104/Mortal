# 预计算进度日志与编码提速

Status: ready-for-agent

实施状态：2026-10-01 已完成，见 [验收记录](acceptance.md)。

范围：Q39–Q44 已由用户全部确认；本规格的增量已写入正式模块并通过有限验收，临时实验替换函数没有接入生产流程。

## Problem Statement

预计算使用者启动全量生成后，直到任务完成才看到最终输出，无法从终端判断程序是否正在推进、已有多少成果可恢复，或剩余时间主要消耗在哪个阶段。此前运行约两小时仍无进度日志；一次短时采样估算剩余处理需要约八天。

改动前 Rust 与 PyTorch CPU 线程默认均为 4，尚未针对实际生成链路选择较合适的组合。固定语义编码已经确定每类观测的存储方式，但编码过程仍复制整行后再只取一列，部分通道选择产生的非连续布局又使后续 reshape 复制大数组。此外，编码重复执行筛选阶段已经完成的观测逐值语义检查，增加扫描与临时数组成本。

使用者已有可恢复的预计算成果。改进应当显示真实的提交进度、降低生成时间和内存开销，同时保持样本精度、排列、chunk 格式与旧恢复状态兼容。

## Solution

预计算入口在启动、恢复、目录扫描开始、chunk 成功提交、split 切换和任务完成时输出即时刷新的命令行日志。周期默认每成功提交一个 chunk，可配置；进度展示使用已提交成果，速度使用本次运行的增量，恢复状态中不加入性能统计。

采用默认 Rayon 16、PyTorch CPU 1、文件批次 4 的可配置运行参数。编码直接取整行标量的第一列，连续提取逐牌通道并尽早将二值数据转为紧凑表示。完整观测语义检查继续由筛选阶段负责，编码阶段保留必要结构及标签检查，信任已经筛选且在恢复期间保持稳定的输入。

在已经完成的有限真实数据实验中，原配置平均约 1,556 样本/秒，调线程后约 2,106，结合编码优化后约 2,890；峰值 RSS 从约 7.2 GiB 降到约 5.1 GiB。这些是实现方向的证据，不是全量完成时间或硬件资源上界的承诺。

## User Stories

1. As a 预计算使用者, I want 启动时立即看到任务信息, so that 我知道命令已经进入生成流程。
2. As a 预计算使用者, I want 恢复时看到已有成果和游标, so that 我能确认旧进度已被正确读取。
3. As a 预计算使用者, I want 在开始扫描牌谱目录时看到提示, so that 枚举大量文件时也能了解当前阶段。
4. As a 预计算使用者, I want 默认每成功提交一个 chunk 显示一次进度, so that 长时间任务持续提供可见反馈。
5. As a 预计算使用者, I want 可以调整日志的 chunk 间隔, so that 我能在反馈频率和终端输出量之间选择。
6. As a 预计算使用者, I want 最后不足一个日志周期时仍看到结果, so that 尾块成果不会缺少反馈。
7. As a 预计算使用者, I want 看到 train 到 val 的切换, so that 我知道当前处理的数据集部分。
8. As a 预计算使用者, I want 完成和已完成后再次启动都有明确提示, so that 正常退出不会看起来像未运行。
9. As a 预计算使用者, I want 输出立即刷新, so that 在终端或重定向输出时均可及时看到日志。
10. As a 预计算使用者, I want 看到完整提交牌谱数和牌谱总数, so that 我能了解当前 split 的处理比例。
11. As a 预计算使用者, I want 按牌谱数量显示完成百分比, so that 不必预先计算全部样本就能观察进度。
12. As a 预计算使用者, I want 看到累计已提交 chunk 和样本数, so that 我能判断当前可恢复的数据成果。
13. As a 预计算使用者, I want 尚在 buffer 中的样本不被计作已提交, so that 日志不会夸大能够恢复的工作。
14. As a 预计算使用者, I want 一份牌谱只有全部样本进入已提交 chunk 后才计作完整完成, so that 跨 chunk 的文件不会被提前计数。
15. As a 预计算使用者, I want 恢复后保留累计成果但重新累计速度, so that 旧任务成果不会使本次速度虚高。
16. As a 预计算使用者, I want 看到本次运行耗时及牌谱和样本速度, so that 我能比较不同配置的实际效率。
17. As a 预计算使用者, I want 看到当前 split 的估算 ETA, so that 我能安排后续工作。
18. As a 预计算使用者, I want 尚无速度依据时如实显示 ETA 不可估算, so that 启动或恢复初期不会出现误导性时间。
19. As a 预计算使用者, I want 看到 C/D 已提交数据用量和配置预算, so that 我能观察跨盘容量消耗。
20. As a 预计算使用者, I want 看到相对路径游标和样本 offset, so that 我能核对恢复位置。
21. As a 性能调优者, I want 分别看到 Rust 提取、GRP 推理、Python 样本整理、编码压缩和写盘提交的累计耗时, so that 我能定位主要时间成本。
22. As a 预计算使用者, I want 日志与计时只用于展示, so that 恢复契约不因增加统计字段而复杂化。
23. As a 预计算使用者, I want 只有文件与进度都提交成功后才显示新增成果, so that 写盘或进度保存失败不会产生虚假的成功日志。
24. As a 预计算使用者, I want 默认使用实测较快的线程组合, so that 新启动任务可获得已验证的性能改进。
25. As a 预计算使用者, I want Rust 线程、PyTorch CPU 线程和文件批次继续可配置, so that 我能适配其他硬件或后台负载。
26. As a 预计算使用者, I want 编码减少重复数据复制, so that CPU 时间和主机内存被用于有效工作。
27. As a 预计算使用者, I want 二值观测尽早转成紧凑数组并保持连续布局, so that 后续展开形状和位打包不反复搬运大副本。
28. As a 预计算使用者, I want 生成阶段信任前置筛选的观测语义结论, so that 每个 chunk 不再重复承担逐值扫描成本。
29. As a 数据维护者, I want 筛选入口继续完整检查观测语义, so that 削减编码重复检查不会降低前置筛选标准。
30. As a 预计算使用者, I want 编码仍拒绝结构、标签及奖励中的必要约束错误, so that 运行异常会明确失败而不会被静默修补。
31. As a 模型训练者, I want 连续观测保留 float32、奖励保留 float64, so that 提速不引入数据精度变化。
32. As a 模型训练者, I want 新生成 chunk 的格式和样本顺序与旧版兼容, so that 现有 reader 与训练流程可继续消费数据。
33. As a 预计算使用者, I want 已有 incomplete 状态和已提交 chunks 可继续使用, so that 无需丢弃已经完成的预计算工作。
34. As a 预计算使用者, I want 仅调整线程或日志频率时仍能恢复, so that 运行参数变化不会被误认为样本语义变化。
35. As a 维护者, I want 通过公开入口和既有编解码接口验证改动, so that 测试能发现可观察行为错误并允许内部实现调整。
36. As a 数据维护者, I want 验证和性能复测使用有限输入及独立临时产物, so that 正式数据和运行进度不会被测试修改。

## Implementation Decisions

- 本轮保留现有预计算入口与 `run_precompute` 的职责：按排序输入生成六元样本，填充固定大小 buffer，编码并通过存储层提交。所需变更落在预计算编排、样本生成计时、公共 codec、独立配置解析及相关说明中。
- 新增正整数配置 `log_every_chunks`，默认 1。配置缺少该键时采用默认值；拒绝零、负数和非整数等无效值。该键属于运行参数，不加入不可变生成契约。
- 预计算默认参数改为 `rayon_threads=16`、`torch_threads=1`、`file_batch_size=4`。解析器默认值、示例配置和本链路的实际配置同步更新，保留用户已有路径、配额及其他配置值；仍允许显式配置其他合法线程数与批次。
- Rayon 参数须在本进程第一次使用 Rust 并行运行时前生效；PyTorch 参数控制 CPU 算子内并行。文件批次和线程数不相乘解释为固定 worker 数。
- 启动、恢复、目录扫描开始、split 切换和完成事件不受周期日志间隔限制。周期以本次成功提交的 chunk 计数，尾块同样计入；split 末尾不足一个周期时补充最后的进度。所有输出及时 flush，继续保留最终结果摘要。
- 已经 complete 的数据集启动后输出明确的已完成信息并退出，不启动新的生成或重置累计成果。
- 周期进度至少包含当前 split、完整提交牌谱数/总数与百分比、累计已提交 chunk/样本、本次耗时、牌谱/样本速度、当前 split 的 ETA、C/D 已提交字节与预算、相对路径游标及样本 offset。各项统计清楚标示对应 split 或全数据集，避免口径混用。
- 牌谱百分比的分母来自现有有序文件发现结果，不预先提取全部样本来计算总样本数。复用已有文件列表与处理位置，不在每条日志输出时重新扫描目录。
- buffer 中的样本不计入已提交成果。跨 chunk 的牌谱只有其全部样本进入成功提交的 chunk 后，才增加完整牌谱计数；恢复时正确区分游标位于文件中间或恰好位于文件末尾，不能一律把游标文件算作完整完成。
- 恢复启动时展示旧累计数和游标；计算速度时只使用本次新增提交的样本和新增完成的牌谱，耗时仅属于本次运行。正常重读游标牌谱和跳过旧样本不能虚增新增工作量。
- ETA 使用当前 split 剩余牌谱数量和本次可用处理速度估算。尚无速度依据时标明不可估算；空 split 和完成状态正确处理，避免除零和无穷大。不把 ETA 解释为精确截止时间或剩余样本总量。
- 计时使用单调时钟，输出五段本次累计耗时：Rust/libriichi 提取、GRP 奖励推理、Python 样本整理、编码压缩、写盘与进度提交。划分实际执行边界，避免把包含子阶段的生成总时间再次叠加；累计阶段耗时不强行归属为每个 chunk 的独占耗时。
- 文件发布与进度原子提交成功之后，才输出对应 chunk 的成功进度。存储层可能已更新内存对象但进度写入失败时，不能从该内存对象再发出虚假的成功或完成摘要；异常继续抛出。
- 性能计数、速度、ETA 和阶段耗时仅保存在本次内存中并输出到终端。恢复 JSON 的 schema、字段含义、生成 ID、样本 offset、chunk 分配区间与完成状态保持兼容，现有只在 split 完成时填写的源文件总数字段不改作周期计数。
- 完整观测语义校验继续供筛选入口使用，检查整行一致性、二值取值、NaN/Inf 等。生成编码路径不再重复执行这些逐值观测检查，也不删除或削弱筛选所用的校验能力。
- 编码保留 observation 形状/dtype、字段长度、非空 chunk、动作和标签范围、二值合法动作 mask、动作属于 mask、折扣步数范围及有限奖励等既有必要约束。错误直接终止，不增加自动修复、重新分类或运行时容错。
- 省去重复观测检查的前提是牌谱已完成筛选，并遵守同一次生成及恢复期间输入内容、冻结奖励模型与样本语义稳定的既有约定；接受不再二次发现观测语义异常的取舍。不增加源码哈希、逐文件哈希或新的筛选证明文件。
- 整行相同的二值和连续通道直接提取第一列，避免先复制 34 列再保留一列。通道类别继续由固定语义布局确定，不根据实际值重新猜测类别。
- 逐牌通道以适合样本顺序展开的连续布局提取；已知二值数据尽早转为 uint8，再按原位序打包，减少 float32 副本及 reshape 复制。连续值不做量化。
- 编码保留现有格式头、版本、字节序、位顺序、字段顺序、Zstd 等级、float32 观测与 float64 奖励。对符合固定语义的输入，解码后的六元样本保持精确相等，已有 chunks 和现有 reader 无需迁移。
- 保持模型 CPU float64/eval 推理方式、奖励定义及文件/玩家/决策顺序；不将 GRP 转到 GPU，不引入跨牌谱推理合批来改变浮点执行方式。
- 保持每 chunk 提交、尾块、跨盘路由和从文件内 offset 恢复的行为。旧版已提交成果继续被认可，不为启用日志或调整线程重建数据集，也不重复读取全部旧 chunks 验证身份。
- 公共 codec 的设备解码仍采用 PyTorch 延迟导入，避免编码优化重新增加筛选 worker 的训练运行时依赖。
- 性能优化以已有临时实验为依据，正式实现采用普通模块代码；不把实验中的动态源码替换、临时 monkey patch 或网格控制脚本接入产品流程。

## Testing Decisions

- 主要测试 seam 沿用公开 `run_precompute` / CLI：观察终端输出、实际生成的 chunk、公开解码结果以及持久化进度；优先扩展现有全量生成与中断恢复用例。
- 辅助回归复用现有 codec 公开编解码接口和筛选测试边界，分别验证格式兼容性与前置检查完整性。不给每个计时辅助函数、私有数组选择表达式或日志拼接函数建立一套独立测试接口。
- 参考既有 unittest、临时目录、可控样本生成器及提交失败注入方式；需要稳定时间断言时可注入轻量计时/输出依赖，断言字段与业务含义，不锁定无关空格、耗时实数或内部对象结构。
- 验证默认和自定义日志周期、启动/恢复、目录扫描、split 切换、最后余量、无尾块时的结束、空 split、complete 再次启动和输出及时 flush。
- 对可独立核对样本数的小数据验证牌谱数、百分比、chunk 数和样本数，包括一谱跨多块、多谱拼一块、游标位于谱内及恰好位于谱末。buffer 和提前生成的数据不能被计作已提交成果。
- 在旧 schema 的 incomplete 状态上恢复，验证累计数衔接、增量速度不包含历史工作、ETA 只针对当前 split；确认计时和统计不新增持久化字段或更改生成 ID。
- 注入 chunk 写入失败和“文件已发布但进度未提交”的失败，验证不输出失败 chunk 的成功进度或整体完成消息；恢复后没有漏样本或重复采纳未登记 chunk。
- 使用受控时间覆盖五段累计耗时与恢复后重置，不重复计算嵌套阶段，不依赖测试机器执行速度建立通过门槛。
- 用代表性有效输入和覆盖四类语义通道的构造样本验证编码往返；使用优化前的参考结果或独立预期比较顺序、二值位序、连续 float32 与奖励 float64，不能只用同一新算法计算期望值。
- 验证旧 chunks 仍能被现有 reader 解码、新编码结果满足相同格式；必要时使用少量真实牌谱对照奖励与全部样本字段，而非只比较数量。
- 筛选回归需证明整行不一致、非法观测二值和 NaN/Inf 仍被前置检查拒绝。编码路径继续验证形状/dtype、标签、mask 和奖励等保留约束；不再要求编码器拒绝已明确交由筛选负责的逐值观测错误。
- 保留 codec 轻量导入与 CPU 解码回归；环境支持时使用小型张量复核设备解码，不启动正式训练。
- 配置回归覆盖省略日志键时的默认值、显式自定义值、无效日志周期、16/1/4 默认值以及调整线程/日志参数后对旧进度的恢复；核对实际配置与示例的受影响键。
- 正式实现后进行有界的相同输入对照，包含满块、尾块、编码与提交成本，记录吞吐和峰值 RSS，并核对输出精确性。线程对照使用新进程，候选顺序运行；不把不同线程组合同时运行而造成的资源争抢当作网格结果。
- 性能数字受输入分布、缓存和负载影响，不在常规测试中断言固定 1.86 倍加速或固定内存上限。此前 34 次实验是设计依据，正式版本需要自己的有限验收记录。
- 需要真实盘写入时仅使用独立临时目录，测试输入只读或使用副本，自动清理临时 chunk；不改动正式牌谱、既有 chunks、权重、报告或运行进度。

## Out of Scope

- 新增生成 worker 进程池、Python 线程池流水线、异步编码或多进程共享观测传输。
- 在阻塞的单次调用内提供定时心跳、后台轮询进度或热更新正在运行的 Python 进程。
- 自动重启或继续用户的正式预计算任务。
- 将性能统计写入恢复状态、增加独立统计数据库、日志轮转或强制持久化日志文件。
- 精确预知全量样本或 chunk 总数、保证固定倍数加速或全量完成日期。
- 更改筛选规则、去掉筛选的观测语义校验，或新增与输入稳定约定重复的防御性机制。
- 更改观测/奖励精度、chunk schema、压缩等级、样本顺序、奖励计算语义或主模型训练逻辑。
- 改造 Rust/PyO3 接口、将 GRP 推理迁移至 GPU、采用跨牌谱 GRP 合批。
- 无上限网格搜索、全量牌谱重算、批量重建已有 chunks 或正式长训练。
