最终方案见 [implementation-plan.md](implementation-plan.md)，硬件资源预算与 GPU 微测见 [resource-estimate.md](resource-estimate.md)。本文保留逐轮讨论记录。

## 已明确的需求

1. 提供独立筛选入口，遍历 `data/grp/train`、`data/grp/val`，检查基础规则，通过 libriichi 实际提取样本并检查必要约束；不计算奖励。按每门赤五最多一张校验，将有问题的牌谱移入 `data/grp/quarantine/<split>/<原相对路径>`。
2. 数据问题尽量在筛选阶段解决；后续仅保留必要检查，遇到错误直接终止，不静默忽略。
3. 为筛选后的全部 train、val 牌谱分别生成六元样本，按文件名顺序处理，不在生成阶段打乱。
4. 使用按样本数量限制的 buffer，默认 16,384 个样本、可配置；达到阈值后编码为 chunk 并落盘，清空 buffer；末尾余量也保存成 chunk。
5. 生成与编码属于同一可独立运行流程；chunk 保存到 `data/precomputed_chunks/train`、`data/precomputed_chunks/val`。
6. 在 `data/precomputed_chunks` 下用 JSON 保存预计算进度，区分完成与待继续；启动时尝试恢复，无进度文件则从头开始。
7. 按观测语义固定二值/连续、整行标量/逐牌元素四类，二值按位打包，连续观测保留 float32、奖励 float64，采用 Zstd level 1。不再逐 chunk 扫描判定偶然全零/全一。
8. 主策略训练读取预计算 chunk，以随机生成并持久化的种子打乱 chunk 和内部样本。CPU 解压成紧凑数组，目标设备按 batch 展开，CPU 最多预取一个 chunk；跨 chunk 拼 batch，训练 Brain、DQN、AuxNet，保存 checkpoint 与 TensorBoard。
9. 在 `artifacts/<本次训练目录>` 用一个 checkpoint 同时保存模型、优化器、学习率状态、必要随机数状态、seed、epoch 和样本游标；若开启 AMP 则保存其状态。没有恢复文件则从头开始并清空该训练目录；存在但损坏则报错。
10. 初始化时确定并保存种子和排列生成规则，内部排列读到对应 chunk 时按需生成；初始化恢复记录立即保存，此后与 checkpoint 同频率更新。
11. 加入离线验证，验证也消费预计算 chunk；周期保存时评估固定可复现子集，每个 epoch 结束评估全量 val。
12. 整个新预计算链路重新编写，不复用旧链路代码；不能把旧格式、旧压缩方案、旧训练器和复杂防御机制当作默认设计。
13. 所有影响行为、性能、兼容性和复杂度的未明确选择，先给建议并由用户决定；全部方案满意且明确授权后才能实现。
14. 已选择 float32 无损观测缓存，物理目录为 `/mnt/c/MortalChunks`、`/mnt/d/MortalChunks`，缓存预算分别 320、440 GiB；train 优先 D、再 C，val 在 C，项目目录通过目录链接提供统一入口。
15. 每写完一个 chunk 才提交预计算进度，保存下一个牌谱及其内部位置，不持久化 buffer。恢复时可重算未提交部分；已写出但未登记的当前 chunk 按未提交处理。
16. 同一次预计算及其恢复期间，源牌谱集合与内容、冻结奖励权重及样本生成规则保持不变；不引入源码哈希或全量文件内容哈希。
17. 第一版由一个 Python 调度进程每批取四份排序后的牌谱交给 Rust 并行处理，再按原顺序进行 CPU 奖励计算和汇总。Rust 与 PyTorch CPU 线程数都必须可配置，初始建议各四线程。
18. 每轮最后的小 batch 保留，照常做一次优化更新，不补假样本、不额外按该批占目标 batch 的比例缩小梯度。
19. 新链路的筛选、样本生成、奖励计算、编码、读取和训练循环全部重写；继续使用 libriichi 和 `mortal/model.py` 的网络定义。训练目标采用 Q 值回归、CQL 和局结束后顺位分类。
20. 缺少预计算进度 JSON 时从头开始，自动清除本次预计算专用输出目录中的旧 chunk 和临时 chunk；不清理源牌谱或其他数据。
21. 用户已接受 Q21–Q29 的奖励、模型、优化器、运行参数、验证频率、筛选边界、格式和新目录；并要求提供当前硬件下的内存/显存预算。本轮已完成短小 GPU 合成测量，未实现新链路。

## 只读核实的现状

- 初始 `git status --short` 无输出，工作区干净。
- Rust 支持 observation v1–v4；v4 为 `(1012, 34)`，动作空间为 46。来源：`libriichi/src/consts.rs`。
- 现有六元样本为 `(obs, action, mask, steps_to_done, kyoku_reward, player_rank)`。`player_rank` 指局结束后的顺位标签，不能一概称作整场最终顺位。来源：`mortal/transformer_pipeline/dataloader_with_grp_transformer.py:395`。
- 当前 Transformer 样本生成器对 action 不在 mask 中的样本执行跳过。因此直接复用旧迭代器会影响“发现错误”和“全量样本”的定义。来源：同文件 `:465`。
- 只调用 GameplayLoader 无法覆盖后续 Python 索引、奖励模型和编码的全部前置条件。仓库的 `validate_logs` 也没有执行完整样本生成路径，不能直接视为新筛选器。
- 现有缓存编码根据整个 chunk 的实际值分类，并将连续观测转为 float16；这会改变部分原始 float32 值。来源：`mortal/transformer_pipeline/precomputed_cache.py:139`。
- 观测语义支持固定分类，但不能假定所有通道都在每个样本内恒为整行标量；单人表部分通道会根据决策场景写逐牌连续值。来源：`libriichi/src/state/obs_repr.rs:564`。
- 当前训练目标由 DQN 回归、CQL 项和下一局边界顺位分类组成。目标 Q 值使用 `gamma ** steps_to_done * kyoku_reward`。来源：`mortal/transformer_pipeline/train_mortal_offline_with_grp_transformer.py:685`。
- 现有缓存训练只跑一次遍历，要求初始 checkpoint；保存模型与优化状态，但恢复时会重新读取、解码已完成 batch 后跳过。来源：`mortal/transformer_pipeline/train_with_precomputed_cache.py`。
- 根目录 `config.toml` 只有 GRP 和 Transformer-GRP 配置，不足以直接启动主策略训练。现有实验配置是事实参考，尚未选为新方案默认值。
- 最初沙箱内探测显示 16 个逻辑 CPU、约 15.2 GiB WSL 可见内存，GPU 查询受限；后续沙箱外只读查询确认 CPU 为 Ryzen 7 9700X、Windows 可见内存 31.14 GiB、GPU 为 RTX 4090 约 24 GiB。六步合成数据 GPU 测量见资源文档，仍不是新链路实测。

## Q10–Q20 已确认决定

用户逐项接受本轮推荐，Q12 特别强调 Rust、PyTorch 线程数必须可配置。以下记录已接受的行为；明确标注尚待细化的部分不属于已决定参数。

- **Q10 编码方案**：按二值/连续、整行标量/逐牌元素固定四类；二值按位打包，连续观测 float32，奖励 float64；使用 Zstd level 1。不在每个 chunk 内重新扫描判定偶然全零/全一。最终容器和整型位宽已在 Q28 确认。
- **Q11 chunk 与供数**：默认每 chunk 16,384 个样本，可配置；CPU 解压成紧凑数组，目标设备按 batch 展开完整观测；CPU 最多提前读取一个 chunk。当前 chunk 的紧凑数组可常驻设备，完整观测不整块常驻。Q23 已确认默认 batch=1,024，完整 obs 为约 134.4 MiB；16,384 条的完整 obs 为 2.10 GiB、紧凑 obs 为 167.9 MiB。
- **Q12 生成并行方式**：第一版一个 Python 调度进程，每批按排序取四份牌谱交给 libriichi 的 Rayon 并行提取，按原次序计算 CPU 奖励并汇总。先以四个 Rayon 线程、四个 PyTorch CPU 线程为可配置起点，不引入 Python 多进程传递大 observation 数组。具体吞吐需要测量，不能视为最优配置。
- **Q13 预计算恢复边界**：每完成一个 chunk 再提交 JSON，保存下一份牌谱和该牌谱内下一样本位置；中断后重算尚未提交的 buffer，游标落在牌谱中间时重读该谱并跳过已提交部分。不持久化整个内存 buffer。已写出但未登记的当前 chunk 按未提交处理，恢复时重建；精确跨盘命名/清理规则随后细化。
- **Q14 输入稳定性**：同一次预计算及其恢复期间，源牌谱集合、内容、奖励权重和生成语义保持不变。只保存必要配置及位置，不引入源码哈希和全量文件内容哈希；若要变更这些输入，则从头生成一套新数据。训练阶段的可调参数边界另行讨论。
- **Q15 训练持久化**：一个 checkpoint 同时保存模型、优化器及学习率状态、AMP 状态（若开启）、随机数状态、seed、epoch 和已消费样本游标；原子替换这个文件。第一步训练前保存初始 checkpoint，不另设可独立漂移的进度 JSON。Q24 已确认默认每 1,000 batch 周期验证并保存。
- **Q16 最终不足一批的样本**：每轮末尾保留全部样本，最后小 batch 正常进行一次更新，不补假样本。其平均损失不按该批占目标 batch 的比例额外缩放。CPU 事实检查表明模型支持 B=1，但 GPU/compile 路径尚未测试。
- **Q17 网络和学习目标**：新写筛选、样本生成、奖励计算、编码、读取和训练编排；底层 libriichi 与 `mortal/model.py` 的网络定义继续使用。损失数学为 Q 值回归 + CQL + 局结束后顺位分类，具体参数已在 Q21–Q23 确认；不从旧链路导入训练函数。
- **Q18 离线验证**：周期保存时评估固定且可复现的验证子集，每轮结束再评估全量 val；验证不更新网络。子集大小、频率、指标和保留策略已在 Q24 确认。
- **Q19 物理目录及配额**：使用 `/mnt/c/MortalChunks`、`/mnt/d/MortalChunks` 的专用目录，项目目录链接到它们；C 预算 320 GiB、D 440 GiB。每个完整 chunk 不能超过所在卷剩余预算，train 优先 D、val 放 C。
- **Q20 缺失预计算进度文件**：按照用户要求视为从头开始；如果专用输出目录已有旧 chunk，自动清除本次预计算专用目录中的旧 chunk 和临时 chunk 再生成；不能擅自清理其他数据。

只读补充验证：使用 mortal Conda 环境的 `python -B` 构造 v4 Brain（192 通道、40 块）、DQN、AuxNet，training=True 且 no_grad，仅做 B=1 的 CPU 前向。81 个 BatchNorm 的输入均为 `(1, 192, 34)`，三个网络输出形状正常且有效输出有限；没有 CUDA 初始化、反向传播、checkpoint 加载或新增字节码缓存。此结果只证明小 batch 的模型结构可用，不代表上述新供数链路已实现或已测 GPU 性能。

## 确认状态

运行参数与边界已由用户在 Q21–Q29 接受。用户随后确认训练入口和核心流程合并为单个 `train.py`，并接受 Q30–Q32 的文件归属、限定导入和测试就近放置方案；这些内容现已实现。

补充事实：合法对局可能让某位玩家整场没有决策样本，例如东一局早期役满放铳导致飞人终局。因此不能把单视角零样本等同于坏牌谱；现有 Rust 对空视角仍返回一个 `dones=true`，Python 应按明确的空视角规则处理，而非直接用所有字段等长断言拒绝。现有 Python API 足以实现已批准的筛选范围，无须默认扩展 Rust 来做完整逐事件动作审计。

## Q21–Q29 已确认参数与边界

用户逐项接受以下配置，并在 Q22 要求说明当前硬件资源占用。参数用于明确首个实现的行为，不是已验证的最优训练配置；恢复时的变更规则由 Q27 决定。

### Q21 奖励参数

- 权重：`artifacts/grp_transformer.pth`，CPU float64/eval 推理，按 Q14 在本次预计算期间保持不变。
- 网络：d_model=128、nhead=4、num_layers=4、max_seq_len=60。
- 一至四位的名次效用：`[6.0, 4.0, 2.0, 0.0]`。
- 主策略奖励折扣 gamma=1.0；chunk 仍保留 steps_to_done 和原始局奖励，不预先固化折扣后的 Q target。

### Q22 主模型与优化参数

- v4 Brain：192 通道、40 个残差块；DQN v4；AuxNet 输出四个顺位类别；BatchNorm 正常更新。
- 联合损失：`0.5 * MSE(Q, gamma**steps * reward) + 5.0 * CQL + 0.2 * rank_cross_entropy`。
- AdamW：lr=1e-4，betas=(0.9, 0.999)，eps=1e-8；仅 Linear/Conv1d 的 weight 应用 weight_decay=0.1。
- 初版默认恒定学习率，无 warmup、无梯度累积、无梯度裁剪；每个 batch 正常执行一次优化尝试。恢复保存优化器中的当前学习率；不为恒定学习率引入旧链路的调度器实现。

### Q23 训练执行配置

- device=`cuda:0`；batch_size=1024，可配置；初始 num_epochs=1，可配置。
- CUDA AMP 默认开启（float16 autocast + GradScaler）；它影响训练计算精度，不改变已确认的 float32 无损缓存。
- `torch.compile` 首版默认关闭，提供可配置开关；cuDNN benchmark 默认开启，可配置。
- 初始随机 seed 在每次从头训练时生成并立即持久化；每个 epoch 使用由主 seed 和 epoch 编号确定的新排列，恢复不重新抽主 seed。
- 设备不足或不可用时报错，不静默更换设备或 batch size。

### Q24 保存、日志与验证

- 每 100 个已消费训练 batch 写 TensorBoard 汇总；每 1,000 个 batch 做周期验证并保存 checkpoint，均可配置。
- 周期验证固定取 131,072 个样本（不足时全取）；独立的 validation_seed 默认 0，使同一数据集的不同训练运行使用同一验证子集。
- 每轮结束全量验证；所有平均指标按真实样本数量加权。
- 指标：总损失、DQN/CQL/顺位损失、顺位分类准确率、Q 值与目标均值、学习率、样本进度和吞吐。
- 只维护一个可恢复的 `latest.pth`，不默认保存历史快照或另一个 best checkpoint。
- TensorBoard 恢复时隐藏未提交 checkpoint 之后的旧事件；验证中断时恢复后重跑必要验证，不能让半次验证成为恢复依据。

### Q25 筛选边界

- 输入按当前四人麻将的 100,000 总点数规则检查，守恒包含供托，普通五与赤五合计最多四张、每门赤五最多一张。
- 单玩家视角零样本是允许的，保留其余玩家样本；不以该空视角的特殊 dones 长度误判整谱。
- 四家合计零样本，或超过选定 GRP 的 60 局容量：按“本链路不可用”隔离，原因区别于牌谱规则错误，不静默截断牌谱。

### Q26 隔离布局及筛选续跑

### Q27 完成状态与恢复时的配置变更

- 预计算完成时再次启动正常退出，不重新编码；进度存在但无法解析则报错，不按“文件不存在”清空数据。
- 已完成训练若 num_epochs 未增加则正常退出；提高到更大的目标轮数时从下一轮继续。
- 恢复可调整线程数、日志/保存频率、设备、compile/benchmark 开关和增加磁盘预算；不悄悄变更网络、batch size、AMP 模式、损失或优化器语义。

- 每次从头生成数据时创建一个生成 ID，训练 checkpoint 记录它；同一路径的数据被重新生成后，旧 checkpoint 不得直接接续。只比较这个 ID、格式及必要参数，不引入源码哈希或逐文件内容哈希。
- 两盘达到预算或写入失败时停止，保留已提交进度；调整可用预算后恢复，不自动突破预算。

### Q28 chunk 容器及进度大小

- 每个 chunk 使用一个新的固定布局二进制文件：短头部含格式版本和样本数，正文按固定顺序放数组，整体 Zstd-1 压缩。
