## 当前瓶颈

每份牌谱依次经过：Python gzip 解压、Python JSON/规则检查、Rust `GameplayLoader.load_log()`、Python 样本适用性检查。外层严格一份完成后再开始下一份。

Python 3.12.13 是常规 GIL 构建。`GameplayLoader.load_log()` 没有显式释放 GIL，但 Rust 内部会用 Rayon 并行处理四家视角。因此：

- 当前不是完全单线程，实测进程曾使用约 2.6 个 CPU 核心。
- Python `ThreadPoolExecutor` 不能让多个 `load_log()` 稳定并行，预期收益有限。
- 多进程拥有独立 GIL，能并行执行整份牌谱检查；每个进程仍需限制内部 Rayon 线程，避免过度并发。
- Rust 批量接口能并行文件，但保留现有 Python 规则检查时会重复读取 gzip；一个坏文件还会让整批调用失败并需要定位重试。

## 小规模只读基准

同一批 24 份 train 牌谱，只读取和校验，不移动文件、不写报告或进度：

| 组合 | 吞吐 | 相对现状 | worker 峰值 RSS 合计 |
| --- | ---: | ---: | ---: |
| 现状单进程 | 3.81 份/秒 | 1.00x | 未单独测量 |
| 2 进程 × 4 Rayon | 6.03 份/秒 | 1.58x | 未单独测量 |
| 4 进程 × 2 Rayon | **6.84 份/秒** | **1.79x** | 未单独测量 |
| 4 进程 × 1 Rayon | 4.57 份/秒 | 1.20x | 2.39 GiB |
| 8 进程 × 1 Rayon | 6.37 份/秒 | 1.67x | 4.76 GiB |

这是短基准，包含进程启动成本，不能保证全量长期速度。按 6.84 份/秒静态外推，约 145 万份牌谱需要约 59 小时；长谱分布、文件缓存和其他负载会改变结果。

随后对同一位置的 96 份牌谱做了更长基准：

| 组合 | 吞吐 | 平均使用逻辑核 | 16 逻辑核利用率 | worker 峰值 RSS 合计 |
| --- | ---: | ---: | ---: | ---: |
| 4 × 2 | 7.23 份/秒 | 6.81 | 42.6% | 2.96 GiB |
| 6 × 2 | 8.35 份/秒 | 10.16 | 63.5% | 4.29 GiB |
| 8 × 1 | 7.12 份/秒 | 7.62 | 47.6% | 5.59 GiB |
| **8 × 2** | **10.01 份/秒** | **13.26** | **82.9%** | **5.55 GiB** |
| 8 × 3 | 8.52 份/秒 | 13.94 | 87.1% | 5.53 GiB |
| 10 × 2 | 9.76 份/秒 | 14.60 | 91.3% | 6.80 GiB |

更高 CPU 利用率没有继续提高吞吐。8×3 和 10×2 的额外 CPU 时间消耗在更多任务调度、Rayon 同步、缓存与内存带宽竞争上。8×2 是本次样本中的最高吞吐点；相对单进程长跑速度仍需实现后用更多牌谱确认。

旧实现中每个 worker 会间接导入 PyTorch，峰值约 0.62 GiB。现已把 codec 的 PyTorch 导入延迟到设备解码函数；2,000 份基准中 8 个 worker 的 RSS 合计峰值降至约 2.33 GiB。

## 推荐协调模型

推荐 `spawn` 创建校验进程池，主进程仍是唯一提交者：

```text
排序文件流
  -> 有界派发给只读 worker
  -> worker 完整校验一份文件，只返回成功或不可用原因
  -> 主进程按原文件顺序移动坏谱、追加报告、推进游标
  -> 每 100 份顺序提交 progress.json
```

worker 不移动文件、不写报告和进度，也不把 observation 或 Gameplay 返回给主进程。这样可以保留当前隔离和恢复语义。

已完成但等待前序文件的结果也计入在途窗口。初始建议窗口为 `2 × workers`，不能一次提交百万个 Future。

主进程可以先收到后方任务的未知异常，但只有连续、成功取得结果的文件才能产生隔离副作用并推进游标。一旦出现未知异常、Rust panic 或 worker 异常退出，停止派发和后续提交，取消尚未开始的任务；已提前读取但未提交的文件在恢复时自然重查。

## 最终实施方案

配置新增：

```toml
[quarantine]
worker_processes = 8
rayon_threads_per_worker = 2
max_in_flight = 16
```

三个字段必须是正整数，且 `max_in_flight >= worker_processes`。用户可以按其他机器资源调整；当前机器默认使用实测最高吞吐的 8×2。

入口使用 `multiprocessing.get_context('spawn')` 和 `ProcessPoolExecutor`。worker initializer 在首次调用 libriichi 前设置 `RAYON_NUM_THREADS=2`，并创建一个长期复用的 `SampleApplicabilityValidator`。

主进程以不超过 16 份牌谱的窗口派发任务。worker 返回文件判定、错误原因和三个阶段耗时，不返回 observation。主进程可以乱序接收结果，但只按排序后的连续序号移动坏谱、写报告和推进内存游标。每顺序提交 `commit_every` 份后，沿用现有 `_save_progress()` 写入原格式 JSON。

终端进度示例：

```text
[train] 12500/1277548 (0.98%) rate=10.0 files/s eta=35:10:00 quarantined=2 avg_ms(read/rules/libriichi)=0.4/5.1/92.7 cursor=...
```

`processed/total` 在启动时根据源目录、quarantine 目录和现有游标计算；展示字段不写入 progress。恢复的正确性仍只依赖相对路径游标。

codec 顶层移除 PyTorch 导入，只在 `decode_chunk_torch()` 内局部导入。该变化不修改 chunk 格式、CPU 编解码或训练接口。

## 验证计划

- 用可控制延迟的 worker 验证乱序完成仍按序移动和提交游标。
