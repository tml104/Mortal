# 预计算线程网格与编码性能实验

日期：2026-09-30。用途：为进度日志与提速方案提供测量依据。用户已确认 Q39–Q44 全部推荐方案，[正式规格](../precompute-progress-performance/spec.md)已发布为 ready-for-agent，决定见[讨论记录](precompute-progress.md)。本文保留 2026-09-30 的实验数据；2026-10-01 正式功能和配置已更新，新旧正式实现的独立比较见[验收记录](../precompute-progress-performance/acceptance.md)。原正式数据未修改。

## 结论

原 4/4/4 配置的 128 份真实 D 盘对照平均约 1556 样本/秒。仅改为 Rayon 16、PyTorch 1、文件批次 4，平均约 2106 样本/秒（1.35 倍）；减少编码复制、使用连续数组布局并信任前置筛选的临时实验版本平均约 2890 样本/秒（1.86 倍）。

后者进程峰值 RSS 约 5.1 GiB，原配置约 7.2 GiB。用户已通过 Q42 确认省去重复观测检查，通过 Q43 确认线程配置 16/1/4，通过 Q44 确认减少复制和连续布局。同等优化已经用普通模块代码实现；实验中的动态函数替换没有接入生产流程。

## 测量方法与边界

- CPU 为 Ryzen 7 9700X，8 核/16 逻辑线程，WSL 可见内存约 15.2 GiB。
- 每组使用新进程，在第一次调用 libriichi 前设置 Rayon，避免全局线程池初始化后环境变量调整无效。候选依次执行，不彼此抢占 CPU。
- 固定使用当前恢复点之后的牌谱，先以 32 份构造 21,972 条样本、一个满块和一个尾块进行短测，再用 128 份构造 85,613 条样本、五个满块和一个尾块进行对照。
- 每组先用四份牌谱预热；计时不包含模型初始化和预热，包含现有生成、buffer 复制、编码、压缩、chunk 写盘和进度提交。
- 短测输出在 /tmp；较长对照把 chunk 写入真实 /mnt/d 上独立创建的临时目录，仍执行 fsync 和原子替换，进度 JSON 位于 WSL 临时目录，与正式布局对应。所有临时 chunk 已自动清理。
- 校验在计时结束后执行：全部非奖励紧凑字段按 chunk 比较摘要，float64 奖励直接逐位比较。所有候选均与原配置一致；未采用容差放宽。
- 128 份输入集中于游标附近两天的牌谱，不代表全部年份。主要候选有重复测量，其他格点仅一次；因此不能把单次短测名次或数个百分点差异说成稳定的全局最优。
- RSS 是进程高水位，不是 Windows 整机内存；离散采样时 swap 均未占用，没有连续测量 swap 峰值。

## 线程参数含义

| 参数 | 控制范围 |
| --- | --- |
| rayon_threads | Rust 的全局 Rayon 池；跨文件和四家玩家视角共享该池 |
| torch_threads | CPU GRP Transformer 算子内部并行；不是同时推理多少份牌谱，也不是 GPU 线程 |
| file_batch_size | 一次交给 Rust 的文件数；影响并行工作量及内存中观测数据量 |

生成、buffer 填充、编码与写盘目前顺序衔接。NumPy 的选择、复制、位打包以及当前默认单线程 Zstd 不会因为增加前两项线程数自动变快。批量 PyO3 加载入口未释放 GIL，也不能直接用 Python 线程池保证多次加载重叠。

## 分段证据与编码改动

较长对照中，原 4/4 配置的 Rust 提取约 30.2 秒，GRP 推理约 0.54–0.61 秒，编码约 17–19 秒；编码内重复观测检查约 7.5–10.6 秒。D 盘提交 chunk 的总耗时约 0.3–0.5 秒，这批数据下不是主要瓶颈。检查耗时是编码总耗时的一部分，不能重复相加。

优化前 codec 对标量通道先选择完整 34 列再取第一列，形成无用的大副本；选取逐牌通道的高级索引还可能产生非连续布局，后续 reshape 再复制。实验改为直接选择标量值、采用连续布局选取逐牌通道并较早转成紧凑二值数组，保持现有字段顺序、位打包和 float32/float64 表示。

保留所有观测检查的连续布局版本约 2,447 样本/秒、6.27 GiB；信任前置筛选的版本约 2,870–2,910 样本/秒、5.13–5.15 GiB。后者不再二次检查每个观测值，但保留形状、dtype、标签合法性、有限奖励等现有必要检查。用户已确认采用后者，并继续遵守已筛选输入与生成语义稳定的约定。

最新检查显示独立筛选进度为 complete；仍须遵守同一批输入内容与生成语义在恢复期间不变的既有约定。线程与文件批次不在不可变生成契约中，调整它们可沿用当前 739 个已提交 chunk。

## 多进程与进一步并行

不能把筛选的 8 个 worker 原样套过来：筛选只返回小型判定，生成若返回 dense 样本则一份约 650 样本的 observation 已接近 85 MiB；如果每个进程都持有完整 chunk buffer，8 份 buffer 本身就约 16.8 GiB，超过当前 WSL 可见内存。

后续若需要更高吞吐，可以另行设计有界生成与编码流水线，但须明确数据传输方式、峰值内存和顺序提交。此次没有实现或测量这种架构，不把其潜在收益计入当前提速结论。

8.1 天是上一轮短时间速度外推，不是全量承诺。仅按这次约 1.86 倍的完整路径速度比例换算，大致为 4.3 天；实际日期分布、冷缓存、切换磁盘及系统负载会改变该估计。
