# 新预计算链路磁盘空间估算

测量日期：2026-09-23；2026-09-27 更正 WSL2 物理容量判断。用户已确认 float32 无损、四类语义编码、Zstd-1、C/D 目录与配额，以及固定布局二进制容器和整型位宽。没有修改旧链路或生成正式 chunk。

## 结论

按本次观测抽样、固定语义编码及 Zstd level 1 的候选布局，分别对 train、val 外推：

| 项目 | 连续观测保留 float32，无损 | 连续观测转 float16，有损 |
| --- | ---: | ---: |
| train | 552.2 GiB | 405.4 GiB |
| val | 77.2 GiB | 56.7 GiB |
| 合计 | 629.4 GiB（675.8 GB） | 462.1 GiB（496.2 GB） |
| 在合计基础上另留 20% 的空间预算 | 755.3 GiB | 554.5 GiB |

此前记录的约 900.8 GiB（967.2 GB）仅为 WSL2 ext4 虚拟磁盘内文件系统的逻辑空闲量。此前据此判断两种方案都能直接放入项目目录的结论不成立：VHDX 的实际增长受宿主机所在卷容量限制，不会自动合并 C/D 空闲空间。2026-09-27 查询 C 约剩 428.3 GiB、D 约剩 532.8 GiB，float32 中心估计超过任一单盘可用量，需要另行选择存储布局或压缩方案。

20% 是规划余量，不是统计置信区间，也不是可证明的最大占用。

float16 方案中心估计少用约 167.3 GiB，但会改变部分原始观测数值。float32 无损方案并非不压缩，也不需要保存全部裸张量。

## WSL2 分盘存储（目录与配额已确认，尚未创建）

`findmnt -T /home/tml104/Mortal/data` 显示项目位于 `/dev/sdd` 的 ext4 文件系统；`df -hT` 显示 `/mnt/c` 和 `/mnt/d` 分别是 Windows C/D 卷，通过 WSL 的 9p 挂载访问。Linux 根文件系统报告的空间不能与 C/D 可用空间相加。

Windows 只读注册表查询未能启动，错误为 `UtilBindVsockAnyPort: socket failed 1`，未取得当前 Ubuntu VHDX 路径。因此没有确认它在 C 还是 D，也没有确认 C/D 是否位于不同物理磁盘。

用户已接受将独立 float32 无损 chunk 分别保存在 C/D，并确认以下具体路径和链接布局。当前没有创建这些目录或链接：

```text
data/precomputed_chunks/
  progress.json
  train/
    c -> /mnt/c/MortalChunks/train/
    d -> /mnt/d/MortalChunks/train/
  val -> /mnt/c/MortalChunks/val/
```

逻辑上仍有一个 train 集合、一个 val 集合。chunk 路径带有存储子目录，训练时汇总全部 train chunk 后统一打乱；同一个 chunk 不拆到两个卷。

已确认的预算如下：

| 卷 | 当时可用 | 缓存预算上限 | 按 629.4 GiB 中心估计实际写入 | 预算用满后仍保留 |
| --- | ---: | ---: | ---: | ---: |
| C | 428.3 GiB | 320 GiB | 约 189.4 GiB | 约 108.3 GiB |
| D | 532.8 GiB | 440 GiB | 440 GiB | 约 92.8 GiB |

已确认让 D 优先承担最多 440 GiB 的 train，其余 train 和全部 val 放 C。按中心估计，C 包括约 112.2 GiB train 与 77.2 GiB val。两盘预算合计 760 GiB，略高于之前另加 20% 的 755.3 GiB 规划值；这是显式的文件分配，不是可用空间自动合并。

为避免占用双份完整数据，候选生成流程在内存编码后直接写目标盘；临时文件也放在该盘对应目录，完成后在同一文件系统重命名，再更新进度。精确提交和恢复规则仍待后续讨论。

性能取舍：WSL 访问 `/mnt/c`、`/mnt/d` 的文件系统开销通常高于本机 ext4，实际训练是否受影响尚未测量。chunk 大小与预取策略需后续确定。若需要原生 ext4 路径，可另讨论每个卷上的独立 VHDX，但这涉及额外磁盘创建、挂载和恢复管理，目前不建议默认引入。仅将当前单个 WSL VHDX 从 C 移到 D，也不会让它同时使用两盘容量。

## 数据规模与测量方法

- 通过只读遍历目录实际计数：train 1,277,547 份 `.json.gz`；val 173,554 份；合计 1,451,101 份。未解压全量牌谱。
- 各 split 按完整文件名排序，分成八个等宽位置区间，在每个区间中点取连续八份文件，共 64 train + 64 val。
- 位置公式：第 i 个块从 `floor((i + 0.5) * file_count / 8) - 4` 开始取八份，并约束在文件列表有效范围内，i 从 0 到 7。
- 使用现有 libriichi 扩展的 `GameplayLoader(version=4, oracle=False, augmented=False, player_names=[])` 重新提取原始 float32 观测。没有从旧 float16 缓存反推 float32。
- train 测得 42,565 个样本，平均每份 665.078125 个；val 测得 43,844 个样本，平均每份 685.0625 个。合计 86,409 个样本。
- 每八份牌谱为一个测量块，实际块大小为 4,668–6,006 个样本。该测量边界不代表新链路最终 chunk 大小。
- 依源码语义将观测分为四类。对所有抽样观测检查二值性、整行恒值约束以及 `(1012, 34)` 形状，全部通过。
- 二值按位打包，整行连续量只保存一个标量，逐牌连续量保留所有位置；连续量分别使用 float32 和 float16。
- 将上述四个数组按固定顺序拼成字节流，分别做 Zstd level 1 压缩，仅统计字节数。没有使用旧链路编码器，没有写正式 chunk，没有运行 GRP 或主模型。
- 测量耗时约 78.8 秒，原始小型测量记录保存在 `/tmp/mortal-new-precompute-space-estimate-20260923.json`；该临时文件不是实现依赖。

## 外推公式与其他字段

各 split 分别计算：

```text
预计样本数 = 测量样本数 × 全量文件数 / 64
预计磁盘字节 = (测量 observation 压缩字节 + 测量样本数 × 18) × 全量文件数 / 64
```

18 B/样本是其余五个字段的紧凑表示预算：action 1 B、46 位 mask 向上取整 6 B、折扣步数 2 B、reward 8 B、rank 1 B。该位宽已在 Q28 确认，可表示范围在筛选阶段约束；此估算保守地不计这五个字段进一步压缩的收益。

外推约 968,563,900 个样本。仅 observation 的磁盘外推为 float32 613.2 GiB、float16 445.9 GiB；其他五字段预算为约 16.2 GiB，得出表首的 629.4 与 462.1 GiB。

对照不同压缩层次，仅 observation 的全量估算为：

| 表示 | 预计空间 |
| --- | ---: |
| 裸 float32 张量 | 121.24 TiB |
| 固定语义编码、float32、尚未做通用压缩 | 9.47 TiB |
| 固定语义编码、float16、尚未做通用压缩 | 5.72 TiB |
| 固定语义编码 + Zstd，float32 | 613.2 GiB |
| 固定语义编码 + Zstd，float16 | 445.9 GiB |

因此仅做语义编码尚不足以满足当前磁盘容量，本次候选估算依赖后续通用压缩。

## 与已有缓存交叉对照

读取 `artifacts/precompute_optimize_10k_v1/manifest.json`：旧缓存选取 10,000 份训练牌谱，共 6,569,869 个样本，实际 chunk 合计 3,300,201,110 字节，约 502.32 B/样本。

简单按当前 train + val 文件总数外推旧 float16 格式，为 446.0 GiB。它与本次新语义布局的 float16 observation 外推 445.9 GiB 接近；加上本次对其他字段不压缩的预算后为 462.1 GiB。

这只能作为量级交叉检查：旧缓存只抽取 train，格式与样本分组方式不同，不能当成新格式的实测全量结果。

## 局限

- 新候选布局只测了 128 份牌谱，未跑全量生成，筛选后的实际样本数尚未知。
- 后续已确认 chunk=16,384、短二进制头、紧凑进度、不保存每样本来源坐标及 Zstd-1；与本次按八份牌谱分块的条件不同，实际压缩率仍需验证。
- 表首中心值不计容器/元数据、训练 checkpoint 与 TensorBoard。20% 额外预算用于规划余量，不保证覆盖任意后续设计。
- 没有测试 float16 对模型质量的影响，也没有测量磁盘吞吐或 GPU 解码性能。
- 测量当时用于比较两种候选精度；用户随后批准 float32、Zstd-1、位宽和容器，完整布局仍需实现后的往返及容量验证。
