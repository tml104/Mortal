# 优化训练按运行保存日志与逐行时间：设计讨论

日期：2026-10-09。

状态：Q67–Q72 已由用户全部确认采用推荐，并按后续指令完成规格、拆票和实施。正式规格见[spec.md](spec.md)，实现与验证见[验收记录](acceptance.md)。本文件保留原设计及问答历史。

## 整体确认稿

- 范围为当前 train_optimize 训练入口。每次启动自动在配置的模型保存目录建立日志，文件名 `log-YYMMDD-hhmmss.log` 取启动时刻；同秒同名时追加，跨日运行继续使用该文件。
- 文件与终端同时输出同样的 Python 层内容，包含进度、告警和异常堆栈；每个物理行以 `[YYMMDD-hh:mm:ss] ` 开头，多行和空行同样处理，两侧使用同一行时间并立即刷新。
- 文件名及逐行时间统一使用固定 Asia/Shanghai、24 小时制。文件名使用本次启动时间，行前缀使用该行的实际记录时间；速度、耗时和 ETA 仍使用既有单调时钟。
- 从头训练保留符合本次固定命名格式的历史日志，清理其余旧产出；正常恢复保留历史日志。该选择明确覆盖旧方案“无 checkpoint 时清空整个目录”的约定，当前运行日志也不能被清理掉。
- 日志无法建立或写入失败时终止训练，并尽可能在终端说明原因。不增加重试、异步队列、逐行 fsync、轮转或日志恢复索引。
- 路径/输出范围的必要检查仍先保证可安全建立日志；配置尚无法读取或保存目录无法确定/不可写时在终端报告失败，不猜测其他日志目录。日志生命周期须保证已建立日志之后的 Python 异常堆栈能在退出前记录，且恢复原始输出流、关闭文件；避免重复时间前缀或重复记录异常。
- 不保证捕获 Rust/C++ 或编译子进程绕过 Python 流直接写底层描述符的输出。新日志机制与 checkpoint、数据样本和 TensorBoard 指标语义独立，不给每个 batch 增加 GPU 同步或设备访问。
- 更新日常启动说明，使模型目录中的自动日志成为主要日志；文件名和内容在公开训练入口验证，并覆盖多行告警/异常、恢复/从头清理、同秒追加、写入失败及输出资源关闭。

## 已明确的要求

- 优化训练日志默认保存到模型保存目录；沿用当前 train_optimize 链路范围。
- 文件名为 `log-YYMMDD-hhmmss.log`，日期时间取本次启动时刻；一次运行跨日仍使用该启动文件名。
- 日志每个物理行以 `[YYMMDD-hh:mm:ss]` 开头，后接原有内容；行时间表示该行记录时刻。
- 既有样本进度、保存位置、指标、速度和阶段 ETA 的口径继续适用；耗时和速率仍使用单调时钟，文件/行日期使用墙钟。
- 这次需求没有要求日志轮转、数据库、日志恢复索引、GPU 心跳或新的后台托管工具。

格式示例（仅展示格式）：

```text
artifacts/mortal_precomputed_optimize/log-261009-231200.log
[261009-23:12:00] event=resume epoch=4 ...
[261009-23:12:08] event=first_batch_start ...
```

## 已核对的事实

- TrainingProgress.emit 当前调用立即刷新的 print，只输出到 stdout，没有管理日志文件。
- 当前后台启动记录指向外部重定向日志。只读检查普通及提权进程列表均未发现优化训练进程；旧记录的日志文件当前也不存在，不能将历史 PID 当作仍在运行。
- 实际配置中的 output_dir 为 `./artifacts/mortal_precomputed_optimize`，从仓库根启动时即模型保存目录。
- 从头训练没有 checkpoint 时会清空该目录，再保存初始状态；正常恢复则保留目录内容。若先打开目录内日志，再按旧代码清空，日志路径会被删除，因此初始化顺序/清理范围必须配合设计。
- Python 告警与异常堆栈通常写 stderr，且可能包含多行；只给进度 print 加前缀无法覆盖这些输出。
- 当前 WSL `/etc/timezone` 为 Asia/Shanghai，本地时钟为 CST、UTC+08:00。
- 当前代码没有热重载，新日志行为由后续实现后的启动应用；本轮不执行启动或恢复。

## 本轮问答历史：已结束

以下保留原问题与建议供追溯；用户已统一回答“Q67-72全部采用你建议的做法”，当前结论见上方整体确认稿。

### Q67：文件与终端输出

保存到文件时是否继续向终端输出同样内容？

建议：同时写文件与终端，两侧使用同一时间前缀并立即 flush，延续原先终端进度反馈。之后后台启动无需再指定额外固定 train.log 作为主要训练日志。

### Q68：日志覆盖范围

文件是否只收集本程序的进度消息，还是同时记录 Python stdout/stderr 中的告警、错误和异常堆栈？

建议：记录训练进度与 Python 层 stdout/stderr，逐个物理行加时间，包含多行告警和异常堆栈。该范围不承诺捕获绕过 Python 输出流、直接写底层文件描述符的 Rust/C++ 或编译子进程输出；若也需要覆盖这些，应明确增加底层捕获范围及相应实现成本。

配置无法读取、保存目录尚不能确定或不可写等情况下，仍需要能从终端看到启动失败；不增加猜测日志目录的自动回退。

### Q69：时区

使用固定北京时间，还是跟随运行机器的本地时区？

建议：文件名和行时间统一固定 Asia/Shanghai、24 小时制，与用户时间一致；本次不增加可配置时区选项。

### Q70：从头训练与历史日志

日志移入模型目录后，沿用此前“从头清空整个输出目录”会删除旧日志。是否继续这一约定，还是保留历史按运行日志？

建议：保留符合本次固定命名格式的日志，其余旧训练产物仍按从头训练规则清理。正常恢复也保留历史日志。这明确调整此前整体清空约定；新日志必须在清理中保留或在清理后创建，不能被删除路径。

用户决定：采用推荐，日志保留例外已确认。

### Q71：同秒文件名冲突

如果同一输出目录在同一秒重复启动，要求的秒级文件名会相同。应追加、报错，还是允许增加后缀？

建议：追加到同名文件，使用已有 start/resume 消息区分运行，保留原内容；不增加编号后缀或等待机制。正常单次运行仍对应启动时间文件；同秒启动是合并的例外，本需求不增加并发训练锁。

### Q72：日志失败

日志文件无法创建或写入失败时，是否直接终止，还是仅提示后继续训练？

建议：直接报错终止并在可用终端说明，避免使用者以为日志持续保存。保持立即 flush，不要求逐行 fsync，不引入重试、异步日志队列或独立恢复状态。
