# 主模型训练性能调查与临时实验（2026-10-05）

## 结论与操作范围

当前训练有明确提速空间。最有证据的方向是 PyTorch 编译、减少 CPU 逐个提交 GPU kernel 的开销、统一卷积数据排列，以及适度增大 batch。显存占满不是合适的单一目标：原网络 batch 2048 比 3072/4096 快，6144 则出现严重显存压力。

本轮只在 `.scratch/train-performance-20261005/` 新增临时实验程序和记录，没有修改正式训练源码、网络定义或配置。正式训练在新的第 423,000 批 checkpoint 提交后停止；全部实验使用该 checkpoint 初始化独立模型，实验权重没有写回正式 checkpoint。共运行 42 个案例，41 个成功，6144 压力案例主动终止。

## 实验方法和可比边界

每个案例启动独立进程，从相同 checkpoint、种子和样本游标构造模型及优化器。预热 15 批，然后测量 60～180 批；计时两端同步 CUDA。编译实验限制 `TORCHINDUCTOR_COMPILE_THREADS=2`，正常 PyTorch CPU 线程默认 8。

- `resident`：同一真实 batch 已常驻 GPU，衡量计算侧性能。
- `reader`：使用正式 reader 的真实 chunks、确定性乱序和跨 chunk 拼 batch；临时变体也复用这些顺序规则。
- 下面主表全部是 reader 实验；不包含首次编译、周期验证和 checkpoint 保存。
- 显存列采用 PyTorch **预留峰值**，不是 nvidia-smi 的整卡占用；CUDA Graph 私有池会使 allocated 指标不适合作为唯一依据。系统显示、CUDA 上下文等还会占用额外显存。
- 这是短时性能筛选，不能证明长时间训练速度、模型收敛或棋力。不同案例首次编译的缓存状态不同，因此预热耗时不宜横向比较为严格冷启动指标。

基线 reader 三次为 10,947、10,945、10,840 样本/秒，后续百分比以 10,945 为参照。

## 为什么增大 batch 有上限

原网络固定输入扫描结果：

| batch | 样本/秒 | PyTorch 预留峰值 |
| --- | ---: | ---: |
| 1024 | 11,362 | 4.33 GiB |
| 2048 | 14,310 | 8.24 GiB |
| 3072 | 13,540 | 12.27 GiB |
| 4096 | 12,584 | 15.86 GiB |
| 6144 | 未完成计时，主动停止 | 整卡达到 24,057 / 24,564 MiB |

6144 案例超过 139 秒仍没有计时结果，整卡显存已接近上限，功耗却约 135 W。没有观测到明确的 PyTorch OOM 异常；不能把原因直接写成已证实的 OOM 或显存换页，但这个配置表现已足以排除。

编译、内存排列改变后，最优 batch 可能变化。例如布局加普通编译时 4096 又优于 2048。因此不建议按“剩余显存比例”直接计算最终 batch。

增大 batch 还会改变每个 epoch 的优化更新次数、梯度噪声、BatchNorm 更新和 AdamW 按更新步产生的效果。当前 checkpoint 的 `_training_contract` 包含 batch_size，直接改 TOML 恢复会被拒绝。正式采用需要确认实验/迁移方式，并决定学习率、验证/保存/日志频率是否按相同已处理样本数对齐。

## 编译、CUDA Graph 与验证边界

普通编译现有代码已经支持。开启 enable_compile，保留 compile_dynamic=true，即可使用现有路径；这两个开关不在 checkpoint 的训练语义 contract 中。普通动态编译已通过两次完整固定子集验证、切回训练和 216 样本的尾 batch：所有预期更新完成。首次验证约 29.9 秒，第二次约 3.39 秒；包含这些阶段的预留显存峰值约 3.35 GiB。

reduce-overhead 需要新增模式配置及明确的迭代边界处理，当前 TOML 不能直接选择该模式。临时训练循环使用 `torch.compiler.cudagraph_mark_step_begin()`。验证循环另做了三轮对照：

| 验证方式 | 第一次 | 第二次 | 第三次 |
| --- | ---: | ---: | ---: |
| 未显式标记验证迭代边界 | 5.84 s | 60.27 s | 2.34 s |
| 每次验证迭代显式标记边界 | 5.20 s | 2.43 s | 2.41 s |

显式边界消除了本轮第二次验证的大停顿；未标记组第三次也恢复了正常速度，因此不能宣称每次验证都会额外耗时一分钟。标记组完成了三次验证后的训练和尾 batch，共 10 次预期优化更新，预留峰值约 3.73 GiB。此结果支持把正确处理训练/验证边界纳入正式实现，但不是整个 epoch、所有形状和长期恢复路径的完整验收。

## 数据排列为何值得进一步实现

基线 profiler 采样 3 批，共 12,105 个 GPU kernel，平均每批约 4,035 个；其中 2,205 个是 NCHW/NHWC 排列转换，耗时占 GPU kernel 时间约 14.85%。这不是“占全部训练时间 14.85%”。CPU 还需要逐个提交大量小 kernel，因此只增加 CPU 数据读取线程不能解决这部分问题。

临时原型把 Conv1d 表示为高度为 1 的 Conv2d，并将 BatchNorm、通道注意力的归约维度同步对应，贯穿网络使用 channels_last。采样中的这类排列转换 kernel 降到零。真实 32 条输入的 FP32 前向对照最大绝对差异约 2.38e-6，实测案例均有有限指标和实际参数更新。

这是执行表示原型，不是已经可替换的正式网络。权重和优化器状态在本轮实验内作了维度映射；正式方案需要设计与原 Brain/checkpoint 的兼容方式，并补充前向、梯度、恢复与训练效果验证。现有 chunks 的观测语义和内容无需因此重建。

## 其他方向的筛选结论

| 方向 | 本轮证据与建议 |
| --- | --- |
| 减少逐批 GPU→CPU 同步 | train.py 每批 metric_sums.tolist()、mask 的 Python 判断会同步；初测有收益，180 批复测接近基线，不能承诺 6%。可在正式重构时按日志/保存时机再取统计量，保留必要错误检查，但优先级低于编译。 |
| fused AdamW | 一次约 9,940，一次约 11,149 样本/秒，未显示稳定优势。暂不推荐作为主要速度优化。 |
| BF16 | 固定输入约 11,458，对照 FP16 约 11,362，差异小，显存没有实质下降。AMP FP16 已开启；BF16 的数值稳定性可另行研究。 |
| CPU 线程数 | 正式默认 8；改 1 或 4 的 reader 实验约 10,693 / 10,864，无提升。precompute.rayon_threads 和 precompute.torch_threads 不控制当前训练入口。 |
| GPU 常驻紧凑块 | 同一 chunk 仅上传一次，解码逐元素一致；额外约 168 MiB/块。原模型约 11,376；CUDA Graph 1024 约 16,392；2048 约 16,894，未稳定优于相应对照。暂不优先实现。 |
| 更多预取进程/线程、迁移全部 chunks 到 WSL ext4 | 当前 CPU 读取/解压有明显余量，无法指望线性提速。全量数据约 610 GiB，迁移有实际磁盘容量与复制成本；不能把 WSL 虚拟盘显示的空闲量当成独立物理空间。 |
| pinned memory、异步传输/解码、融合解码 kernel、AMP 下直接准备半精度输入 | 仍是候选，但当前证据不足以列为主优化。应在模型计算加速后重新 profile，确认暴露出的数据等待再决定，不能仅凭开启 prefetch 就假设已有完整传输重叠。 |
| 验证与 checkpoint | 当前合计约 5% 时间；放宽频率可节省部分时间，但会降低反馈和恢复频率。保存文件约 125 MiB，不能把这 5% 全归因于写盘。应先优化验证执行，异步保存与大量缓存暂不优先。 |
| cuDNN/TF32/运行环境 | cuDNN benchmark 已开启；主要卷积和线性层已经在 FP16 AMP 下运行，TF32 对这部分没有直接替代收益。现有版本支持本轮所需功能，没有证据要求先升级驱动或环境。 |
| WSL 内存额度/电源/散热 | WSL 尚有约 10 GiB 可用内存，GPU 最高约 60℃，没有证据指向内存或温度瓶颈。先处理已测得的软件开销；本轮没有修改 Windows、电源或驱动全局设置。 |
| 梯度累积、梯度检查点、多进程共享单 GPU | 当前显存不是小 batch 的限制因素；梯度累积/重算不直接提高这条训练的样本吞吐。多进程副本会引入额外状态和竞争，当前更直接的方向是降低单进程提交开销。 |
| 改网络宽深、冻结 BN、学习率策略、减少 epoch | 会改变训练方案或效果，不能仅因显存富余就当作无代价优化。需要另立效果对照。192 通道本身已有良好的 Tensor Core 对齐。 |
| 优化 libriichi | 当前训练消费预计算六元样本，没有重新推进牌谱或计算 GRP 奖励；优化 libriichi 不会直接解决本轮训练瓶颈。 |

## 建议提交用户确认的顺序

1. 低改动方案：保持 batch 1024、网络和损失不变，先采用现有普通编译路径；参考收益约 19%～25%。启动时限制编译线程为 2，与本轮实验一致。仍需一次正式启动/验证/保存/恢复验收。
2. 正式实现 CUDA Graph 模式及训练、验证的边界处理：batch 1024 已测得约 40%～48% 的训练段收益，不必先改变 batch 的训练语义。
3. 是否接受 batch 2048：原链路约 +25%，与编译组合还有进一步收益；需要显式处理 checkpoint、学习率与按样本计量的频率策略。
4. 是否推进 channels_last 执行方案：batch 2048 的布局加 CUDA Graph 已接近原链路的 1.83 倍，且比普通布局编译的 batch 4096 少用显存；这是需要兼容性设计和更充分验证的工程改造。

本轮没有将这些候选应用到正式训练。后台训练已按原配置恢复。
