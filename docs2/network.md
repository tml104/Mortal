# Mortal 网络结构说明

这份文档面向深度强化学习新手，目标不是把所有术语都讲全，而是帮助你快速建立一个清晰的心智模型：

- `Brain` 负责“看懂当前牌局状态”
- `DQN` 负责“给每个可选动作打分”
- `AuxNet` 负责“训练时增加一个辅助学习目标”
- `GRP` 负责“根据对局进展预测最终排名”

从整体上看，Mortal 的主决策流程是：

```text
牌局状态 obs
-> Brain
-> 状态表示 phi（或 v1 中的 latent）
-> DQN
-> 每个合法动作的 Q 值
-> 选择动作
```

训练时还会多接一个辅助头：

```text
phi
-> AuxNet
-> 预测当前玩家接下来的名次类别
```

另有一个独立模型：

```text
对局进程序列
-> GRP
-> 预测最终四家排名分布
```

这里先提前说明一个很重要的结论：

- `GRP` 不是 `Brain` 或 `DQN` 的一部分
- `GRP` 不和主干网络共享参数
- `GRP` 不参与主干网络的动作选择前向过程
- 但是 `GRP` 会参与训练数据中的奖励计算，所以会间接影响主干网络学到什么

---

## 1. 整体输入表示

### 输入

主网络看到的输入叫 `obs`，它是一个形状为 `(通道数, 34)` 的张量。

不同版本的通道数不同：

- v1: `(938, 34)`
- v2: `(942, 34)`
- v3: `(934, 34)`
- v4: `(1012, 34)`

这里的 `34` 表示日麻的 34 种基本牌种。你可以把它理解成：

- 横轴固定是 34 个牌种位置
- 每个位置上堆了很多“描述当前局面的特征通道”

这些通道不是图片里的 RGB，而是程序从麻将状态里提取出的结构化信息，例如：

- 自己手里的牌
- 河里的牌
- 副露信息
- 局数、本场、供托
- 分数相关状态
- 规则或上下文特征

文档里不逐项展开每个通道的语义，但重要的是：`obs` 已经不是原始文本或 JSON 了，而是 `libriichi` 预处理好的神经网络输入。

### 输出

这一层本身没有输出动作，它只是定义了后面网络将要接收的“原始状态表示”。

### 用途

把复杂的麻将状态转换成一个固定大小、适合卷积网络处理的张量。

### 结构

固定的牌轴长度 `34`，配合大量语义通道。

### 详细解释说明

为什么是 `(通道数, 34)`，而不是一个普通向量？

因为麻将里很多信息都和“牌种”强相关。比如：

- 1m 和 2m 是相邻的
- 某一类牌是否已经打完了
- 某一牌种在手里、牌河、宝牌指示中的关系

把 34 种牌排成一条轴后，网络就能用 `Conv1d` 在牌种维度上滑动，捕捉局部关系，例如：

- 相邻数牌的关系
- 同一花色内的组合关系
- 某牌种在不同信息通道里的对应关系

这比直接把所有信息打平成一个超长向量更适合做“麻将结构建模”。

### 其他说明

如果是 Oracle 模式，还会额外拼接一组隐藏信息通道：

- v1: `(211, 34)`
- v2/v3/v4: `(217, 34)`

普通 Mortal 不使用这些额外隐藏信息。

## 2. Brain：主干状态编码网络

### 输入

- `obs`
- 形状为 `(batch_size, 通道数, 34)`
- 如果是 Oracle 模式，还会额外输入 `invisible_obs`，并与 `obs` 在通道维拼接

### 输出

按版本不同分两种：

- v1 输出 `(mu, logsig)`，都是 512 维向量
- v2/v3/v4 输出 `phi`，是 1024 维向量

这些输出都不是“最终动作”，而是对当前牌局的内部理解结果。

### 用途

把当前麻将局面压缩成一个高层状态表示，供后面的决策头使用。

### 结构

`Brain` 可以粗略看成两部分：

1. 一个很深的 1D ResNet 编码器
2. 一个与版本相关的输出头

主干流程是：

```text
obs
-> Conv1d
-> 多个 ResBlock
-> Conv1d
-> Flatten
-> Linear
-> 1024 维表示
-> 版本相关输出头
```

### 详细解释说明

`Brain` 的作用类似视觉模型里的 backbone。它不直接做决策，而是负责回答：

> “当前这手牌和局面，神经网络应该如何理解？”

在代码里，`Brain` 的核心是 `ResNet`：

```text
Conv1d(in_channels -> conv_channels, kernel=3)
-> num_blocks 个残差块
-> Conv1d(conv_channels -> 32, kernel=3)
-> activation
-> Flatten
-> Linear(32 * 34 -> 1024)
```

其中配置文件通常设置：

- `conv_channels = 192`
- `num_blocks = 40`

所以默认是一个比较深的 1D 卷积残差网络。

更具体地说，这个编码器的固定结构是：

```text
Conv1d(in_channels -> conv_channels, k=3, pad=1)
-> N 个 ResBlock(conv_channels)
-> Conv1d(conv_channels -> 32, k=3, pad=1)
-> activation
-> Flatten
-> Linear(32 * 34 -> 1024)
```

它先把原始观测映射成很多卷积通道，然后通过 40 个残差块逐步抽取更高层特征，最后把整条 34 长度的牌轴压成一个 1024 维向量。

这里最关键的是它用的是 `1D 卷积`，不是 `2D 卷积`。

原因是 Mortal 不是把麻将状态当图片处理，而是把它当作：

- 一条长度为 34 的牌种序列
- 每个牌种上有很多特征

这样做的好处是，卷积核能沿着牌种维度滑动，识别类似下面的关系：

- 数牌之间的邻接关系
- 同一牌种在多个信息通道中的组合意义
- 某些局部牌型模式

最后的 `Flatten + Linear(32 * 34 -> 1024)` 则把所有牌种位置上的信息汇总成一个全局向量，供后续决策模块使用。

你可以把这 1024 维向量理解成：

- 当前手牌强不强
- 哪些打牌路线可能好
- 现在是在防守还是进攻环境
- 各种动作在当前局面中的潜在价值

当然，这些不是显式写在某几个维度上的，而是网络训练后自动学出来的分布式表示。

### 其他说明

`Brain` 是整个 Mortal 里最重的部分，参数量大头基本都在这里。`DQN` 和 `AuxNet` 相对都轻得多。

虽然名字叫 `ResNet`，但这里不是图像分类里那套原封不动的 ResNet，而是一个针对麻将状态做过适配的 1D 版本。

## 3. ResBlock：残差块

### 输入

- 某一层卷积特征图
- 形状大致是 `(batch_size, conv_channels, 34)`

### 输出

- 形状不变的特征图
- 仍然是 `(batch_size, conv_channels, 34)`

### 用途

逐层提炼特征，同时依靠残差连接保证深网络更容易训练。

### 结构

每个 `ResBlock` 由三部分组成：

1. 两层 `Conv1d`
2. 一个 `ChannelAttention`
3. 一条残差连接 `out + x`

根据版本不同，块内部有两种排布：

- post-activation
- pre-activation

### 详细解释说明

如果你是新手，可以把残差块理解成：

> “在保留原始信息的前提下，对特征做一次增量修正”

普通深层网络一层一层堆起来后，很容易出现优化困难。残差结构通过：

```text
输出 = 新提取的特征 + 原输入
```

让网络更容易学习“我只需要改一点点”。

在麻将这种状态很复杂、特征很多的任务里，堆很多残差块可以逐步形成更高级的牌局理解能力。

Mortal 里的残差块不是只有卷积，还在残差分支后接了一个通道注意力模块，这表示：

- 不只是提取新特征
- 还会动态判断“哪些通道现在更重要”

### 其他说明

默认配置下 `num_blocks = 40`，所以主干里会堆很多这样的块。这也是 Mortal 主干较深的原因。

## 4. ChannelAttention：通道注意力

### 输入

- 一个卷积特征图
- 形状通常是 `(batch_size, channels, 34)`

### 输出

- 同样形状的特征图
- 但每个通道会被不同权重重新缩放

### 用途

让网络自动决定“当前局面下哪些特征通道更值得关注”。

### 结构

处理流程是：

```text
特征图
-> 沿牌轴做平均池化
-> 沿牌轴做最大池化
-> 两个结果共享一个两层 MLP
-> 相加后过 sigmoid
-> 得到每个通道的权重
-> 回乘到原特征图
```

### 详细解释说明

可以把它理解成一个“通道级别的音量调节器”。

比如在某一时刻，网络可能发现：

- 某些通道对应进攻信息，很重要
- 某些通道对应防守危险度，很重要
- 某些通道在当前局面没那么重要

那么 ChannelAttention 就会给不同通道不同的缩放系数。

这并不会改变特征图大小，但会改变后续层更重视什么。

代码中它通过两种汇总方式得到通道描述：

- `mean`：整体平均强度
- `max`：最强响应位置

再用一个共享小 MLP 生成权重。

### 其他说明

这是 Mortal 主干里区别于“纯标准 ResNet”的一个重要设计点。

## 5. Brain 的版本差异

### 输入

都是麻将状态 `obs`，但不同版本的通道数不同。

### 输出

- v1: `(mu, logsig)`，各为 512 维
- v2/v3/v4: `phi`，为 1024 维

### 用途

说明 Mortal 的不同版本在“状态表示如何定义”上做过演化。

### 结构

差异主要出现在：

- 激活函数
- 残差块排布方式
- BatchNorm 参数
- 输出头形式

### 详细解释说明

#### v1

v1 先用编码器得到 1024 维表示，然后再过：

```text
Linear(1024 -> 512)
-> ReLU
-> 分成两头
   -> mu_head: Linear(512 -> 512)
   -> logsig_head: Linear(512 -> 512)
```

这表示 v1 不是直接输出一个确定性向量，而是输出一个高斯分布的参数：

- `mu`：均值
- `logsig`：对数标准差

随后在推理时：

- 要么直接用 `mu`
- 要么从这个分布采样一个 latent

这说明 v1 的思路更偏向“随机潜变量表示”。

#### v2

v2 不再输出 `(mu, logsig)`，而是直接输出一个确定性的 1024 维 `phi`。

同时它：

- 把激活函数改成了 `Mish`
- 把残差块改成 pre-activation 风格

整体更像现代一些的残差网络设计。

#### v3 / v4

v3 和 v4 的主干总体上沿用了 v2 的思路，依旧是：

- Mish
- pre-activation
- 输出 1024 维 `phi`

主要改动在 BatchNorm 的 `eps` 参数上。

所以如果你只是想抓大意，可以简单记成：

- v1: 随机 latent 方案
- v2-v4: 确定性 `phi` 方案

### 其他说明

当前仓库里最大版本号是 4。

## 6. DQN：动作价值头

### 输入

- v1 输入是 512 维 latent
- v2/v3/v4 输入是 1024 维 `phi`
- 还需要一个动作合法性掩码 `mask`

### 输出

- 长度为 `46` 的 Q 值向量
- 其中非法动作位置会被强制置为 `-inf`

你可以把每个 Q 值理解成：

> “在当前局面下，执行这个动作有多值得”

值越大，网络越倾向于选它。

### 用途

给所有当前可选动作打分，作为最终动作选择的依据。

### 结构

`DQN` 使用的是 dueling 结构：

1. 一条分支预测状态值 `V(s)`
2. 一条分支预测动作优势 `A(s, a)`
3. 再把两者组合成最终 Q 值

组合公式是：

```text
Q(s, a) = V(s) + A(s, a) - 合法动作上的平均优势
```

### 详细解释说明

为什么不直接输出 46 个动作分数，而要拆成 `V` 和 `A`？

直觉上：

- `V(s)` 表示“这个局面整体好不好”
- `A(s, a)` 表示“在这个局面里，这个动作比平均动作好多少”

这样网络更容易把“局面质量”和“动作相对优劣”分开建模。

Mortal 这里还有一个特别重要的细节：

它不是对所有 46 个动作做平均，而是只对当前合法动作做平均。

这很合理，因为很多动作在某个时刻根本不能选。例如：

- 不能随时立直
- 不能随时吃碰杠
- 不能随时和牌

所以代码里明确使用 `mask` 来：

- 计算合法动作上的平均优势
- 把非法动作最终置成 `-inf`

这样最终选动作时，模型不会错误地挑到非法动作。

### 其他说明

在推理阶段，`engine.py` 默认会选 `Q` 最大的合法动作；如果配置了探索参数，也可以做带温度的采样。

## 7. DQN 的版本差异

### 输入

- v1: 512 维 latent
- v2/v3/v4: 1024 维 `phi`

### 输出

- 都输出 46 个动作对应的 Q 值

### 用途

说明不同版本的动作头复杂度不同，但目标一致，都是“给动作打分”。

### 结构

#### v1

```text
v_head: Linear(512 -> 1)
a_head: Linear(512 -> 46)
```

#### v2

```text
v_head: Linear(1024 -> 512) -> Mish -> Linear(512 -> 1)
a_head: Linear(1024 -> 512) -> Mish -> Linear(512 -> 46)
```

#### v3

```text
v_head: Linear(1024 -> 256) -> Mish -> Linear(256 -> 1)
a_head: Linear(1024 -> 256) -> Mish -> Linear(256 -> 46)
```

#### v4

```text
Linear(1024 -> 47)
-> split into:
   - v: 1
   - a: 46
```

### 详细解释说明

从新手角度可以这样理解：

- v1 的动作头最直接
- v2 / v3 给 value 和 advantage 分支都加了一个小 MLP
- v4 又把两条分支在参数上合并得更紧凑

无论怎么变，本质都还是：

- 先得到状态表示
- 再为每个动作估一个价值

### 其他说明

v4 的实现最轻量，但它依然保留了 dueling 的思想，只是用一个线性层同时产出 `V` 和 `A`。

## 8. AuxNet：辅助训练头

### 输入

- `phi`
- 形状是 `(batch_size, 1024)`

### 输出

- 一个 4 类 logits 向量
- 表示对 `player_ranks` 的分类预测

当前训练里，它的输出可以粗略理解成：

> “当前这个状态表示，是否足够判断玩家接下来的名次相关信息”

### 用途

给主干网络增加一个辅助监督信号，让 `phi` 学到更多和对局结果相关的信息。

### 结构

当前训练代码中：

```text
AuxNet((4,))
-> Linear(1024 -> 4, bias=False)
```

### 详细解释说明

强化学习训练有时监督信号比较稀疏，尤其当主目标只围绕 Q 值时，主干表示可能不够稳定。

于是这里额外加了一个很轻的辅助头，让网络在学习动作价值之外，还顺便学习：

> “这个状态和名次结果之间有什么关系”

训练中对应的损失是交叉熵：

```python
next_rank_loss = CrossEntropy(next_rank_logits, player_ranks)
```

所以 `AuxNet` 本身并不复杂，重点不在于它有多强，而在于它给 `Brain` 提供了额外的学习信号。

### 其他说明

`AuxNet` 只在训练中使用，推理决策时不会用它来选动作。

## 9. GRP：排名预测网络

### 输入

`GRP` 的输入不是主策略网络的 `obs`，而是一段对局进程序列。每个时间步是 7 维向量：

```text
[grand_kyoku, honba, kyotaku, s0, s1, s2, s3]
```

可以简单理解为：

- 当前打到哪一局
- 当前本场、供托信息
- 四名玩家的分数特征

### 输出

- 24 类 logits
- 对应四位玩家最终排名的 24 种排列可能性

进一步还可以把 24 类概率转换成：

- 每位玩家拿第 1/2/3/4 名的概率矩阵

### 用途

根据对局进展预测最终排名分布。

### 结构

它的结构是：

```text
GRU(input_size=7, hidden_size=64, num_layers=2)
-> 取所有层最后时刻隐藏状态
-> Flatten
-> Linear(128 -> 128)
-> ReLU
-> Linear(128 -> 24)
```

这里的 `128` 来自默认配置：

- `hidden_size = 64`
- `num_layers = 2`

### 详细解释说明

为什么输出是 24 类？

因为四名玩家最终排名一共有：

```text
4! = 24
```

种可能排列。

相比“分别预测每个人是第几名”，直接预测 24 个完整排列有一个好处：

- 天然保证结果是一个合法排名排列

不会出现“两个玩家都被预测成第一名”这种不一致问题。

`GRP` 用的是 `GRU`，因为这里输入是“随着对局推进不断增长的序列”，模型需要利用时间信息。

你可以把它理解成：

> “随着每一局推进，GRP 持续更新对最终四家排名的判断”

### 其他说明

代码里把 `GRP` 的模块都转成了 `float64`，这是一个比较少见但明确存在的实现细节。

更重要的是，要区分“独立”到底独立到什么程度：

- 它的参数是单独训练的，训练脚本是 [mortal/train_grp.py](/home/tml104/Mortal/mortal/train_grp.py)
- 它的权重单独保存在 `config['grp']['state_file']`
- 主干网络 `Brain + DQN + AuxNet` 的训练脚本是 [mortal/train.py](/home/tml104/Mortal/mortal/train.py)
- 在主决策前向中，`Brain -> DQN -> action` 这条链路完全不会经过 `GRP`

所以如果你问：

> “GRP 会不会直接改主干网络的输出表示，或者和主干一起端到端反向传播？”

答案是：不会。

它没有参与主干的前向计算图，也没有和主干共享参数，因此不会像一个普通附加分支那样直接更新 `Brain` 的参数。

但是，如果你继续问：

> “那 GRP 对主干是不是就完全没影响？”

答案也不是。

因为在这个项目里，`GRP` 会参与训练数据的奖励构造。也就是说：

- `train.py` 训练主干时，会通过 [mortal/dataloader.py](/home/tml104/Mortal/mortal/dataloader.py) 读取样本
- `dataloader.py` 会加载一个已经训练好的 `GRP`
- 然后把 `GRP` 交给 [mortal/reward_calculator.py](/home/tml104/Mortal/mortal/reward_calculator.py)
- `RewardCalculator` 会先用 `GRP` 估计各时刻的排名概率
- 再把这个排名概率转换成 `kyoku_rewards`
- 最后这些 `kyoku_rewards` 会进入主网络训练里的 `q_target_mc`

也就是说，`GRP` 不会直接参与主干网络前向，但会通过“奖励怎么定义”这件事间接影响主干网络的学习方向。

你可以把这种关系理解成：

- 不是“GRP 是主干的一层”
- 而是“GRP 是主干训练时用到的一个外部评估器/奖励模型”

简化成一句话就是：

> `GRP` 不直接决定主干网络怎么算，但会影响主干网络拿什么目标去学。

如果 `GRP` 的排名预测发生变化，那么：

- 同一份对局日志可能得到不同的 `kyoku_rewards`
- 主干网络看到的训练目标也会变化
- 最终主干学出来的策略也可能不同

所以最准确的说法是：

- `GRP` 对主干网络“没有直接结构上的影响”
- `GRP` 对主干网络“有间接训练目标上的影响”

---

## 9.1 GRP 与主干网络的关系

### 输入

这一节讨论的不是某个张量，而是模块之间的关系：

- 主干网络：`Brain + DQN + AuxNet`
- 独立网络：`GRP`

### 输出

结论分成三层：

1. 参数层面：独立
2. 前向决策层面：独立
3. 训练目标层面：有间接影响

### 用途

帮助你准确理解 `GRP` 在整个项目里的位置，避免误以为它要么“完全属于主干”，要么“完全无关”。

### 结构

它们的关系可以画成：

```text
主决策推理：
obs -> Brain -> DQN -> action

GRP 自己的推理：
对局进程序列 -> GRP -> 排名概率

训练时的间接联系：
对局日志 -> GRP -> 奖励估计 -> train.py -> 更新 Brain/DQN/AuxNet
```

### 详细解释说明

先看“完全独立”的部分：

- `GRP` 不读取 `Brain` 输出的 `phi`
- `Brain` 也不读取 `GRP` 的输出
- `DQN` 选动作时完全不需要 `GRP`
- `train.py` 优化主干参数时，优化器里也没有 `GRP` 的参数

再看“间接联系”的部分：

- 主干网络训练需要奖励信号
- 这个项目里部分奖励不是简单用最终分数直接算，而是通过 `GRP` 预测的排名概率来构造
- 所以 `GRP` 的质量会影响训练样本的 target

这就像你在训练一个学生模型时，旁边放了一个单独的“评分器”：

- 评分器不是学生模型的一部分
- 但评分器决定了学生每道题得到多少分

因此评分器还是会影响学生最终学成什么样。

### 其他说明

在 [mortal/mortal.py](/home/tml104/Mortal/mortal/mortal.py) 里还有一个额外用法：

- 普通对局推理时只用 `Brain + DQN`
- 只有在 `review_mode` 下，程序才会额外加载 `GRP`
- 这时 `GRP` 用来输出 `phi_matrix`，也就是排名概率相关的额外分析信息

所以在正常出牌决策中，`GRP` 也不是必需模块；它更多承担：

- 训练时的奖励辅助
- review/分析模式下的结果解释

## 10. 主策略网络的训练目标

### 输入

训练时主策略部分会用到：

- `obs`
- `actions`
- `masks`
- `steps_to_done`
- `kyoku_rewards`
- `player_ranks`

### 输出

训练本身最终输出不是“一个值”，而是三部分损失：

- `dqn_loss`
- `cql_loss`
- `next_rank_loss`

然后加权求和得到总损失。

### 用途

让 Mortal 不只是学会“当前动作分高不高”，还尽量学得更稳定、更保守，并保留对对局结果的理解。

### 结构

总损失形式为：

```text
loss = dqn_loss
     + min_q_weight * cql_loss
     + next_rank_weight * next_rank_loss
```

### 详细解释说明

#### 1. `dqn_loss`

这是主损失，表示：

> “网络给当前动作的 Q 值预测，和实际回报目标差多远”

代码里目标值是：

```python
q_target_mc = gamma ** steps_to_done * kyoku_rewards
```

然后用均方误差：

```python
dqn_loss = 0.5 * MSE(q, q_target_mc)
```

#### 2. `cql_loss`

这是离线训练时才加的一个保守项：

```python
cql_loss = q_out.logsumexp(-1).mean() - q.mean()
```

直觉上它是在提醒网络：

> “不要把那些没见过或不靠谱的动作估得过高”

对新手来说，只要记住它是在做“保守约束”就够了。

#### 3. `next_rank_loss`

这是 `AuxNet` 对应的辅助分类损失：

```python
next_rank_loss = CrossEntropy(next_rank_logits, player_ranks)
```

它的作用是让主干学到更多与名次结果相关的表示。

### 其他说明

这说明 Mortal 不是“只有一个纯 DQN 损失”的简单实现，而是把：

- 强化学习主目标
- 保守正则
- 辅助监督目标

结合起来一起训练。

## 10.1 训练顺序：先训练 GRP，再训练主干

### 输入

这一节讨论的是训练流程依赖关系，不是某个具体张量。

涉及两个训练入口：

- [mortal/train_grp.py](/home/tml104/Mortal/mortal/train_grp.py)
- [mortal/train.py](/home/tml104/Mortal/mortal/train.py)

### 输出

结论很明确：

- 按当前仓库实现，通常需要先准备好一个 `GRP`
- 然后再训练主干网络 `Brain + DQN + AuxNet`
- 这两个网络默认不是联合训练，也不是同时反向传播训练

### 用途

帮助你理解项目实际推荐的训练顺序，以及为什么主干训练一开始就依赖 `GRP`。

### 结构

当前仓库里的默认依赖关系是：

```text
日志数据
-> train_grp.py
-> 训练出一个 GRP
-> 保存到 config['grp']['state_file']

然后

日志数据
-> dataloader.py 加载这个已训练好的 GRP
-> RewardCalculator 用 GRP 计算奖励
-> train.py 用这些奖励训练 Brain + DQN + AuxNet
```

### 详细解释说明

为什么说“先训练 GRP，再训练主干”？

因为主干训练的数据加载器 [mortal/dataloader.py](/home/tml104/Mortal/mortal/dataloader.py) 在构建样本时，会直接做下面几件事：

1. 创建一个 `GRP`
2. 从 `config['grp']['state_file']` 读取它的参数
3. 构造 `RewardCalculator`
4. 用 `GRP` 预测的排名概率去计算 `kyoku_rewards`
5. 把这些奖励送给 `train.py`

也就是说，主干训练不是到中途才偶尔使用 `GRP`，而是从“样本生成阶段”就已经依赖 `GRP` 了。

因此如果 `config['grp']['state_file']` 对应的模型文件不存在，或者没有可用的 `GRP` 权重，主干训练流程就无法按当前实现正常开始。

从训练职责上看：

- `train_grp.py`
  - 只训练 `GRP`
  - 保存的是 `GRP` 自己的参数和优化器状态
- `train.py`
  - 只训练 `Brain`、`DQN`、`AuxNet`
  - 不会更新 `GRP` 参数

所以当前实现不是下面这种方式：

```text
obs -> Brain -> DQN
seq -> GRP
一起算总 loss
一起反向传播
```

而是这种方式：

```text
先有一个训练好的 GRP
-> 它帮助定义主干训练时的奖励
-> 主干再单独训练
```

你可以把 `GRP` 理解成主干训练前就准备好的“外部评分器”。

- 它不是主干的一部分
- 但主干训练要用它来算目标

### 其他说明

理论上，研究者当然可以自行改成别的训练策略，例如：

- 先训练一版 `GRP`
- 再训练一段主干
- 再用新数据继续训练 `GRP`
- 然后再继续训练主干

也就是“交替训练”。

但这不是当前仓库默认实现。

当前代码最准确的描述是：

- `GRP` 和主干网络分开训练
- 主干训练依赖一个已经存在的 `GRP` 权重文件
- 因此默认顺序是“先有 GRP，再训主干”

如果你只是想记一句最重要的话，可以记成：

> 在这个项目里，`GRP` 更像主干训练前置依赖的奖励模型，而不是和主干同时训练的并联子网络。

## 10.2 从日志到主干训练的数据流图

### 输入

这一节讨论的是“训练数据在系统里怎么流动”，起点是原始对局日志，终点是主干网络参数更新。

主要涉及这些模块：

- `libriichi.dataset.GameplayLoader`
- [mortal/dataloader.py](/home/tml104/Mortal/mortal/dataloader.py)
- `GRP`
- [mortal/reward_calculator.py](/home/tml104/Mortal/mortal/reward_calculator.py)
- [mortal/train.py](/home/tml104/Mortal/mortal/train.py)

### 输出

输出结果是：

- 一批训练样本
- 每条样本对应的奖励目标 `kyoku_rewards`
- 最终用于更新 `Brain + DQN + AuxNet` 的 loss

### 用途

帮助你从全流程角度看清楚：

- 日志是怎么变成训练样本的
- `GRP` 是在哪一步介入的
- 主干网络最终是根据什么目标更新的

### 结构

先看整体图：

```text
原始 mjai 日志
-> GameplayLoader
-> 解析出每一步的 obs / action / mask / done / at_kyoku 等信息
-> dataloader.py
-> 同时提取该局对应的 grp 特征
-> 加载一个已经训练好的 GRP
-> RewardCalculator
-> 用 GRP 预测排名概率
-> 把排名概率转换成 kyoku_rewards
-> 组装训练样本
-> train.py
-> Brain
-> DQN
-> AuxNet
-> 计算 loss
-> 更新 Brain + DQN + AuxNet 参数
```

如果把“谁提供数据、谁算奖励、谁被训练”分层画开，可以看得更清楚：

```text
[数据来源层]
原始 mjai 日志
-> GameplayLoader
-> obs, actions, masks, dones, at_kyoku, grp_feature, rank_by_player, final_scores

[奖励计算层]
grp_feature
-> 已训练好的 GRP
-> 排名概率 matrix
-> RewardCalculator
-> kyoku_rewards

[样本组装层]
obs
actions
masks
steps_to_done
kyoku_rewards
player_ranks
-> 拼成训练样本 batch

[主干训练层]
batch
-> Brain
-> DQN
-> AuxNet
-> dqn_loss + cql_loss + next_rank_loss
-> optimizer.step()
```

### 详细解释说明

下面按顺序拆开讲。

#### 第 1 步：日志被解析成基础训练信息

`GameplayLoader` 会从日志里提取主干训练需要的基本数据，例如：

- `obs`
- `actions`
- `masks`
- `dones`
- `at_kyoku`
- `apply_gamma`

这些数据描述的是：

- 每一步看到了什么状态
- 当时实际做了什么动作
- 哪些动作是合法的
- 这个动作处于哪一局
- 回报该如何向后折扣

到这里为止，还没有用到 `GRP`。

#### 第 2 步：同一局日志里再提取 `grp` 相关特征

`dataloader.py` 还会从每局数据里提取：

- `grp_feature`
- `rank_by_player`
- `final_scores`

这些不是给 `Brain` 直接吃的，而是给 `GRP` 和奖励计算器用的。

#### 第 3 步：用已经训练好的 `GRP` 预测排名概率

`dataloader.py` 在开始构建迭代器时，会：

1. 创建 `GRP`
2. 从 `config['grp']['state_file']` 加载它的参数
3. 创建 `RewardCalculator(self.grp, self.pts)`

之后 `RewardCalculator` 会根据 `grp_feature`：

- 先让 `GRP` 预测每个时刻的排名概率
- 再把排名概率转成期望 pt
- 再求相邻时刻期望 pt 的差值

最终得到：

- `kyoku_rewards`

这一步是主干训练里 `GRP` 介入的关键位置。

#### 第 4 步：组装成主干训练样本

`dataloader.py` 会把每一步整理成一个 entry，大致包含：

- `obs[i]`
- `actions[i]`
- `masks[i]`
- `steps_to_done[i]`
- `kyoku_rewards[at_kyoku[i]]`
- `player_ranks[at_kyoku[i] + 1]`

也就是说，主干训练最终看到的样本里，奖励已经是“经过 `GRP` 处理后的奖励”了。

#### 第 5 步：主干网络根据这些样本训练

进入 `train.py` 后，主干训练使用这些样本做：

- `phi = mortal(obs)`，也就是 `Brain`
- `q_out = dqn(phi, masks)`，也就是 `DQN`
- `next_rank_logits = aux_net(phi)`，也就是 `AuxNet`

然后计算：

- `dqn_loss`
- `cql_loss`
- `next_rank_loss`

最后更新的是：

- `Brain`
- `DQN`
- `AuxNet`

这里不会更新 `GRP`。

#### 第 6 步：谁在更新，谁不更新

这一点很容易混淆，所以单独列出来：

- 会被 `train.py` 更新的：
  - `Brain`
  - `DQN`
  - `AuxNet`
- 不会被 `train.py` 更新的：
  - `GRP`

`GRP` 在主干训练期间只是：

- 被加载
- 被调用
- 被用来算奖励

但不会参与 `optimizer.step()`。

### 其他说明

如果你想最简化地理解这张图，可以记住下面这句：

> 原始日志先被解析成状态和动作，再由一个已经训练好的 `GRP` 帮忙把“排名变化价值”变成奖励，最后主干网络根据这些奖励进行学习。

所以从数据流角度看：

- `GRP` 站在主干训练“前面”
- 主干网络站在参数更新“后面”

它们不是并排一起训练，而是前后依赖关系。

## 11. 推理时如何真正选动作

### 输入

- `obs`
- `mask`
- 可选的 `invisible_obs`

### 输出

- 一个最终动作

更精确地说，中间会先得到：

- 每个动作的 Q 值
- 哪些动作合法

然后再从中挑选一个动作。

### 用途

把网络输出的动作评分真正变成对局中的出牌/吃碰杠/立直等决策。

### 结构

推理流程是：

```text
obs
-> Brain
-> DQN
-> 得到合法动作的 Q 值
-> 默认取 argmax
-> 或按配置做带温度采样
```

### 详细解释说明

在 `engine.py` 里：

- v1 会先得到 `(mu, logsig)`，再决定是否采样 latent
- v2/v3/v4 直接得到 `phi`

之后统一交给 `DQN` 得到 Q 值。

默认情况下，系统会选：

```text
Q 值最大的合法动作
```

但如果打开探索参数，例如：

- `boltzmann_epsilon`
- `boltzmann_temp`
- `top_p`

那么模型也可以不总是贪心，而是在高分动作之间做一定随机采样。

这通常用于：

- 训练时增加探索
- 生成更丰富的对局样本

### 其他说明

所以严格来说，真正的“策略”是：

- 神经网络给分
- 引擎再决定是纯贪心还是带探索地选

## 12. 最后用一句话理解整个架构

### 输入

一个由 `libriichi` 处理好的麻将状态张量。

### 输出

一个当前局面下最值得执行的合法动作。

### 用途

完成日麻 AI 的决策。

### 结构

```text
obs
-> Brain（看懂局面）
-> DQN（给动作打分）
-> action（选最高分合法动作）
```

训练时再加：

```text
phi -> AuxNet
序列 -> GRP
```

### 详细解释说明

如果你只想先抓住最核心的理解，可以记住下面这句话：

> Mortal 的核心思路，就是先把麻将状态编码成一个高层向量，再让价值网络对当前所有合法动作打分，最后选分最高的动作。

其中：

- `Brain` 解决“怎么理解局面”
- `DQN` 解决“怎么评价动作”
- `AuxNet` 解决“训练时怎么让表示更稳”
- `GRP` 解决“怎么额外预测最终排名”

### 其他说明

对新手来说，最值得先读懂的是这三个文件：

- [mortal/model.py](/home/tml104/Mortal/mortal/model.py)
- [mortal/engine.py](/home/tml104/Mortal/mortal/engine.py)
- [mortal/train.py](/home/tml104/Mortal/mortal/train.py)

先把 `Brain -> DQN -> action` 这条主线看懂，再看版本差异和训练损失，会轻松很多。
