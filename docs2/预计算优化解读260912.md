## 1. 总览

预计算把固定的六元训练样本保存为缓存。本文沿样本生成、编码、发布和训练消费，说明各脚本怎样协作。

缓存的单位是 **chunk**，即若干份牌谱展开后的一组样本；`manifest.json` 是缓存完成后的清单，记录可读取的 chunk 及其校验信息。预计算负责生成这些文件，训练负责从中恢复张量：

```text
牌谱 → 六元样本 → 编码后的 chunk → 压缩文件
                                     ↓
主模型更新 ← 训练 batch ← 解码张量 ← manifest 指引读取
```

主策略继续更新 `Brain + DQN + AuxNet`。新增工作集中在固定数据的生成、存储和供给方式，损失与优化沿用共享的 `train_batch()`。

## 3. 背景与优化边界

### 3.1 重复的数据准备

传统 Transformer-GRP 离线训练每次遍历牌谱，都要通过 [`GameplayLoader`](../libriichi/src/dataset/gameplay.rs#L143) 解压、解析事件、推进玩家状态并构造 observation。随后 [`iter_file_samples()`](../mortal/transformer_pipeline/dataloader_grp_transformer.py#L395) 调用冻结 GRP 计算局奖励，映射到逐动作样本，再交给 DataLoader 组批。

当这条 CPU 供数链慢于 GPU 消费速度时，主模型会等待数据。增加 worker 和 Rayon 线程可以提高并行度，也会增加内存和资源竞争；预计算则让后续实验复用已经完成的数据准备结果。

### 3.2 可复用的边界与成本

源牌谱、观测版本、玩家选择、奖励模型及名次效用固定后，六元样本便可提前生成：

```text
obs, action, mask, steps_to_done, kyoku_reward, player_rank
```

各字段业务含义在第 7 章说明。缓存保存奖励和折扣步数，训练时仍按配置计算 `q_target = gamma ** steps_to_done * kyoku_reward`，并重新计算特征、Q 值和梯度；共享优化函数见第 8 章。

若将同一数据用于 R 次实验，可用以下简化模型理解复用收益：

```text
传统方式：R ×（数据准备 + 主模型训练）
缓存方式：一次（数据准备 + 编码写盘）
          + R ×（缓存读取解码 + 主模型训练）
```

这是工作量示意，实际墙钟时间还取决于 CPU/GPU 重叠和供数瓶颈。缓存读取足够快且复用次数增加时，前期生成成本更容易摊薄；只生成并训练一次时，总耗时未必更短。

### 3.3 预计算带来的语义差异

缓存路径与传统路径共享 [`iter_file_samples()`](../mortal/transformer_pipeline/dataloader_grp_transformer.py#L395) 的标签构造逻辑，以及 [`train_batch()`](../mortal/transformer_pipeline/train_offline_grp_transformer.py#L686) 的损失与优化逻辑。两者的训练字段含义一致，输入精度和样本排列存在以下两项差异。

#### 3.3.1 连续 observation 会经过 float16 量化

传统路径直接把 Rust 生成的 float32 observation 交给训练器。缓存路径会把 `constant_float_planes` 和 `dense_planes` 转成 float16，读取时再扩展为 float32；全零、全一和其他二值 plane 通过常量记录或 bit-pack 精确恢复。转换位置见 [`encode_chunk()`](../mortal/transformer_pipeline/precomputed_cache.py#L139) 和 [`decode_chunk_torch()`](../mortal/transformer_pipeline/precomputed_cache.py#L330)。

例如，一个 float32 值经过缓存往返后会发生如下变化：

```text
原始 float32：  0.1000000015
float16 存储：  0.0999755859
恢复为 float32：0.0999755859
绝对误差：      0.0000244156
```

现有 10k 缓存记录的全局最大 observation 量化误差为 `0.000244140625`，低于抽样验证使用的 `5e-4` 阈值。`action`、`mask`、`steps_to_done`、`kyoku_reward` 和 `player_rank` 按当前格式无损保存，因此量化直接改变的是 `Brain(obs)` 的输入。这个微小变化可能继续影响 Q 值、loss 和梯度，但仅凭误差统计无法判断最终模型质量。完整 plane 编码与验证机制见第 10.3 节和第 11.5 节。

#### 3.3.2 两套供数机制形成不同的样本顺序

传统路径依次执行“全局文件打乱、文件分片、worker 连续切分、worker 内文件和局部 buffer 打乱”，再由 DataLoader 组成 batch。缓存路径用 `shuffle_seed` 先打乱 chunk，再打乱当前 chunk 的行号；chunk 尾部不足一个 batch 的样本通过 `carry` 与下一 chunk 拼接。两条路径的实现分别见 [`create_data_loader()`](../mortal/transformer_pipeline/train_offline_grp_transformer.py#L651) 和 [`PackedCacheBatchIterator`](../mortal/transformer_pipeline/precomputed_cache.py#L477)。

例如，假设 batch size 为 4，打乱后得到：

```text
C2 = [h, f, i, g]
C0 = [c, a, b]
C1 = [e, d]
```

缓存迭代器产生的 batch 为：

```text
batch 1 = [h, f, i, g]
batch 2 = [c, a, b, e]  # C0 余量通过 carry 取 C1 的第一条补足
batch 3 = [d]           # drop_last=False，保留最终余量
```

传统 DataLoader 通常会形成另一组 batch 组合和先后次序。AdamW 在每个 batch 后更新参数与动量，后续 batch 会基于更新后的模型计算梯度，所以相同样本集合也可能产生不同的逐步训练轨迹。严格比较两条路径时需要保持源文件集合、初始 checkpoint、batch size 和训练配置一致；当前 10k 缓存与 127 万文件的全量传统训练不具备相同的数据范围。

## 4. 实际执行关系

阅读顺序用于建立理解，运行时遵循下面的产物依赖。奖励权重和初始主策略 checkpoint 均可使用已有兼容文件。

```text
train_grp_transformer.py
  └─ GRP Transformer 权重 ────────────┐
                                     ↓
                         precompute_grp_transformer_cache.py
                                     └─ chunk 文件 + 完整 manifest
                                                      │
已有主策略 checkpoint ────────────────────────────────┤
或 train_offline_grp_transformer.py                    ↓
（可由 bs1024 启动器调用）                   train_precomputed_cache.py
  └─ Brain/DQN/AuxNet 与优化器状态             └─ 新 checkpoint 与完成记录

可选测量：
benchmark_offline_grp_transformer_bs1024.py → 传统供数
benchmark_precomputed_cache.py             → 缓存供数及缓存训练
```

普通离线训练器的 `prepare_grp_snapshot()` 可以创建冻结 GRP 快照；预计算器直接读取配置中的 `grp_transformer.state_file`，要求该文件已经存在。预计算生成无需主策略 checkpoint。缓存训练则需要完整 manifest，以及含三套主网络、optimizer、scheduler、scaler 的初始 checkpoint。

## 5. `_bootstrap.py`：准备子目录导入

### 5.1 用途与输入输出

[`_bootstrap.py`](../mortal/transformer_pipeline/_bootstrap.py#L24) 从自身路径推导源码目录，把上一级 `mortal/` 加入模块搜索路径，供子目录脚本沿用项目的平铺导入。它同时暴露目录常量和迁移兼容摘要，没有独立的训练入口。

### 5.2 整体执行流程摘要

```text
模块导入
  -> Path(__file__).resolve()：定位 PIPELINE_DIR、MORTAL_DIR、REPOSITORY_ROOT
  -> sys.path.insert()：需要时加入 mortal/ 搜索路径
  -> 模块级常量：暴露 PRE/POST_PIPELINE_* 摘要
```

### 5.3 路径与迁移摘要

`Path(__file__).resolve()` 使源码目录定位独立于进程工作目录。若 `MORTAL_DIR` 尚未出现在 `sys.path`，便插入首位，使调用方找到公共模型、配置模块及 `libriichi` 扩展。配置中的相对数据路径仍按工作目录解释。

SHA256 是文件内容指纹。这里保存的 `PRE/POST_PIPELINE_*` 常量列出已知目录迁移前后的精确源码摘要，供训练器判断恢复兼容性；校验逻辑属于训练器。本模块本身不读取权重或数据。

## 6. `train_grp_transformer.py`：产生奖励模型权重

### 6.1 用途与输入输出

该脚本使用按局历史前缀训练 `GRP_Transformer`，输入为训练/验证牌谱和 `[grp_transformer]` 配置，输出包含 `model`、optimizer、steps 与时间戳的 checkpoint。后续样本生成只加载其 `model` 字段，把该网络作为固定奖励估计器。命令见[第 17 章](#run-commands)。

### 6.2 整体执行流程摘要

```text
train()
  -> GRP_Transformer + optim.AdamW：建模，按需 torch.load() 恢复
  -> torch.load() 或 build_file_index()：取得训练/验证索引
  -> GrpFileDatasetsIter.__iter__() → build_iter()
       -> populate_buffer() → Grp.load_gz_log_files()：生成历史前缀
  -> DataLoader + collate()：padding 和 mask
  -> GRP_Transformer.forward_padded()/get_label() + F.cross_entropy()
  -> loss.backward()/optimizer.step()：更新
  -> 周期验证；SummaryWriter/torch.save()：记录指标与 checkpoint
```

### 6.3 建模、恢复与文件索引

[`train()`](../mortal/transformer_pipeline/train_grp_transformer.py#L117) 根据配置选择设备；CUDA 不可用时回退到 CPU。模型及输入使用 float64。已有 checkpoint 会恢复权重、优化器和步数，随后将学习率设置为当前配置值。

文件索引包含 `train_file_list` 与 `val_file_list`。索引不存在或其中路径已经缺失时，[`build_file_index()`](../mortal/transformer_pipeline/train_grp_transformer.py#L102) 根据 glob 重建并保存；已有有效索引不会主动发现新增牌谱。

### 6.4 前缀样本与 batch

[`populate_buffer()`](../mortal/transformer_pipeline/train_grp_transformer.py#L50) 从 Rust `Grp` 提取 `(K, 7)` 局初特征，并生成长度为 `1..K` 的 K 个历史前缀。所有前缀共享真实终局顺位标签。`build_iter()` 在文件批次内打乱样本；训练和验证均配置 `cycle=True`，持续提供数据。

[`collate()`](../mortal/transformer_pipeline/train_grp_transformer.py#L74) 将前缀补齐为 `(B, max_len, 7)`，生成 `(B, max_len)` 的 padding mask，True 表示忽略位置。这样每条前缀只通过有效历史预测终局 24 种顺位排列。

### 6.5 更新、验证与保存

`forward_padded()` 得到 `(B, 24)` logits，`get_label()` 将真实顺位映射为排列编号，交叉熵监督分类。每个 batch 执行一次反向传播和 AdamW 更新。

每 `save_every` 步，`train()` 切换到 eval 并计算 `val_steps` 个验证 batch，再恢复 train 模式。TensorBoard 记录 loss、accuracy 和学习率；`torch.save()` 保存模型及优化状态。至此得到可供下一章加载的 GRP 权重。

## 7. `dataloader_grp_transformer.py`：形成六元样本

### 7.1 用途与输入输出

[`FileDatasetsIter`](../mortal/transformer_pipeline/dataloader_grp_transformer.py#L217) 在通用加载器上增加 Transformer GRP 初始化、四家共享奖励、非法动作过滤和坏牌谱隔离。输入是 Rust 提取的玩家视角与冻结奖励模型，输出是六元动作样本，并可附带来源坐标。

传统训练通过完整数据集迭代读取文件；预计算直接复用 `initialize_grp_model()` 和 `iter_file_samples()`。两种入口共享标签语义，文件错误处理有所区别。

### 7.2 整体执行流程摘要

```text
FileDatasetsIter.__init__()：保存可序列化配置
  -> build_iter() → initialize_grp_model()：在实际数据进程加载 GRP
  -> 基类 load_files() → populate_buffer()
       -> _load_files_with_quarantine() → GameplayLoader.load_gz_log_files()
       -> iter_file_samples()
            -> Gameplay.take_*()：提取动作数组及整场信息
            -> _build_shared_grp_targets()：首次视角计算四家奖励与顺位
            -> iter_file_samples()：核对后续视角、计算步数、过滤非法动作
            -> yield (entry, player_id, sample_idx)
       -> populate_buffer()：entry 加入基类缓冲，交给 DataLoader

预计算调用方直接加载牌谱，再调用 iter_file_samples()，绕过自动隔离流程。
```

### 7.3 初始化与牌谱读取

[`__init__()`](../mortal/transformer_pipeline/dataloader_grp_transformer.py#L233) 只保存 GRP 配置，便于 `spawn` worker 复制数据集。[`initialize_grp_model()`](../mortal/transformer_pipeline/dataloader_grp_transformer.py#L250) 在实际数据进程中构造模型、按需检查权重 SHA256，再通过 `torch.load(weights_only=True)` 和严格参数匹配加载 `model`。模型固定在 CPU/eval，奖励推理不参与主策略反向传播。

传统路径的 [`_load_files_with_quarantine()`](../mortal/transformer_pipeline/dataloader_grp_transformer.py#L345) 先批量解析，失败时逐文件重试；仅隔离可确认的数据错误。隔离限于指定 train/val/test 目录并保留审计记录，未知错误继续抛出。预计算直接调用 Rust loader，遇到坏牌谱会停止，不移动源文件。

### 7.4 提取视角并计算四家共享目标

[`iter_file_samples()`](../mortal/transformer_pipeline/dataloader_grp_transformer.py#L395) 通过 `Gameplay.take_*()` 取得逐动作 observation、action、mask、局号 `at_kyoku`、终点标志 `dones`、折扣标志 `apply_gamma`，以及整场 GRP 信息。`take_*` 转移相应向量，因此同一字段只提取一次。

首个视角调用 [`_build_shared_grp_targets()`](../mortal/transformer_pipeline/dataloader_grp_transformer.py#L308)。设牌谱有 K 局，`grp_feature` 是 `(K, 7)`，每行为：

```text
[grand_kyoku, honba, kyotaku, score_0/10000, ..., score_3/10000]
```

`RewardCalculator.calc_grp()` 对所有历史前缀推理，得到 `(K, 4, 4)` 的玩家顺位概率。按名次效用 `pts` 加权，追加真实终局效用，再取相邻边界差：

```text
V[k, p] = sum_r matrix[k, p, r] * pts[r]
V[K, p] = pts[真实最终顺位[p]]
reward[k, p] = V[k+1, p] - V[k, p]
```

同一牌谱四个视角共享历史与终局信息，因此一次前向即可生成四家目标。后续视角先核对这些信息一致，再选择对应玩家列。辅助顺位标签由局初分数及真实终局分数计算，两次稳定 `argsort` 保持同分时玩家编号较小者在前。

### 7.5 映射动作样本并产出

`iter_file_samples()` 从局末反向计算有效折扣距离：

```text
dones[i] 为真：steps_to_done[i] = 0
否则：         steps_to_done[i] = steps_to_done[i+1] + int(apply_gamma[i])
```

随后检查动作范围及 `mask[action]`，过滤不合法样本。对第 i 个决策，令 `k=at_kyoku[i]`，六元样本的含义为：

| 字段 | 单样本形状 | 取值来源 |
| --- | --- | --- |
| `obs` | v4 为 `(1012, 34)` | Rust 编码的可见状态 |
| `action` | 标量 | 牌谱动作，范围 0～45 |
| `mask` | `(46,)` | 当时的合法动作 |
| `steps_to_done` | 标量 | 距本局结束的有效折扣步数 |
| `kyoku_reward` | 标量 | `reward[k, player_id]` |
| `player_rank` | 标量 | 第 k+1 个边界的顺位，范围 0～3 |

同局动作共享局奖励；`player_rank` 指向本局结束后的边界。函数额外返回 `player_id` 和视角内 `sample_idx`：预计算据此追踪来源，普通 `populate_buffer()` 只将六元 `entry` 加入基类缓冲，再由 DataLoader 组批。

## 8. `train_offline_grp_transformer.py`：复用训练接口

### 8.1 用途与输入输出

该入口从牌谱进行可恢复的 Transformer-GRP 主策略训练，输出模型 checkpoint 和首个 epoch 的完成记录。它还向缓存链路提供 `load_file_list()`、`build_models_and_optimizer()`、`train_batch()` 及原子保存函数，保持两条路径的训练接口一致。

训练契约（contract）记录本次运行的数据、参数和实现身份，并以摘要比对恢复兼容性。它与预计算阶段的缓存生成契约分别保护不同流程。启动方式见[第 17 章](#run-commands)。

### 8.2 整体执行流程摘要

```text
main() → parse_args() → training_lock()/configure_file_logging() → run()
  -> validate_output_paths()/prepare_grp_snapshot()：检查输出并准备冻结 GRP
  -> load_file_list()/validate_full_file_list()：核验索引
  -> random.Random.shuffle()/build_dataset_manifests()：确定文件顺序和分片
  -> build_implementation_manifest()/build_training_contract()：固定训练身份
  -> build_models_and_optimizer()：创建或恢复训练组件
  -> 按文件分片：
       create_data_loader()
         ├─ 完整 batch → train_batch()
         └─ 短 batch → merge_partial_batch() → 拼满时 train_batch()
       -> save_checkpoint() → atomic_torch_save()
  -> train_batch()：处理最终余量；复核输入，save_checkpoint()
  -> validate_completed_checkpoint() → write_completion_marker()
```

预检和已完成 checkpoint 分支在 `run()` 内提前返回；正式训练最终仍会处理未满的尾批。

### 8.3 路径、快照与文件身份

[`run()`](../mortal/transformer_pipeline/train_offline_grp_transformer.py#L861) 限定离线、一次 epoch、无增强及 `opt_step_every=1`。[`prepare_grp_snapshot()`](../mortal/transformer_pipeline/train_offline_grp_transformer.py#L212) 校验源权重，仅在冻结快照不存在时复制，再校验快照；后续 worker 使用同一份稳定权重。

[`load_file_list()`](../mortal/transformer_pipeline/train_offline_grp_transformer.py#L259) 读取指定索引键，[`validate_full_file_list()`](../mortal/transformer_pipeline/train_offline_grp_transformer.py#L288) 检查数量、重复路径、有序路径摘要及 glob 集合，已隔离牌谱也纳入逻辑文件集合。当前配置复用 `train_file_list`，预期 1,277,548 份牌谱；预计算选取子集前也执行这一完整索引核验。

文件列表按 epoch seed 打乱，`build_dataset_manifests()` 为各分片记录路径、大小和修改时间身份。[`build_implementation_manifest()`](../mortal/transformer_pipeline/train_offline_grp_transformer.py#L335) 收集源码、扩展和运行时信息，`build_training_contract()` 再合入模型、数据及优化配置。恢复时通过 `validate_resume_training_contract()` 检查兼容性。

### 8.4 构造组件与单 batch 更新

[`build_models_and_optimizer()`](../mortal/transformer_pipeline/train_offline_grp_transformer.py#L486) 构造 Brain、DQN、AuxNet、AdamW、scheduler 和 GradScaler，并根据配置冻结 BatchNorm、启用 compile。恢复分支加载同一组训练状态；缓存训练则先用该函数创建组件，再自行加载指定的初始 checkpoint。

[`train_batch()`](../mortal/transformer_pipeline/train_offline_grp_transformer.py#L686) 检查合法动作、统一设备和 dtype，计算：

```text
q_target = gamma ** steps_to_done * kyoku_reward
phi = Brain(obs)
q_all = DQN(phi, mask)
q = q_all[日志动作]
loss = 0.5*MSE(q, q_target)
     + cql.min_q_weight*(mean(logsumexp(q_all)) - mean(q))
     + aux.next_rank_weight*CrossEntropy(AuxNet(phi), player_rank)
```

每个 batch 清梯度，执行 AMP 前向、反向和可选梯度裁剪，再调用 scaler 更新优化器并推进 scheduler。缓存路径直接复用该函数；数据读取由外层入口决定。

### 8.5 分片训练、保存与完成

[`create_data_loader()`](../mortal/transformer_pipeline/train_offline_grp_transformer.py#L651) 为当前文件分片建立 Transformer 数据集与 DataLoader，`drop_last=False`。主循环直接训练完整 batch，把短 batch 通过 `merge_partial_batch()` 放入 `pending_batch`，可跨 worker 尾部和文件分片拼接；最终余量也参与训练。

每个文件分片完成后，`save_checkpoint()` 通过 `atomic_torch_save()` 保存三套网络、优化状态、训练契约和 `next_file_offset`。下一次启动从最近完成的分片继续。整个 epoch 结束时先训练尾批，再复核输入身份、保存并回读校验最终 checkpoint，再由 [`write_completion_marker()`](../mortal/transformer_pipeline/train_offline_grp_transformer.py#L808) 写完成记录；已有完成状态也有校验后返回的分支。

## 10. `precomputed_cache.py`：缓存格式与读取器

### 10.1 用途与输入输出

本模块负责六元样本、`EncodedChunk` 和压缩文件之间的转换。预计算器通过它保存样本，缓存训练器通过它恢复张量并组成 batch；共同的数据格式使生产和消费两端能够独立运行。

一个 chunk 收集若干份牌谱产生的样本。编码前，observation 是 `(N, 1012, 34)` 的 dense float32 数组，N 为该 chunk 的样本数；其中每个长度为 34 的通道称为一个 plane。编码器利用各 plane 的常量或二值特征减少存储量，结果放入 [`EncodedChunk`](../mortal/transformer_pipeline/precomputed_cache.py#L45)：

| 属性 | 内容 | 用途 |
| --- | --- | --- |
| `metadata` | schema 版本、样本数、观测形状、分类数量及量化/体积统计 | 描述编码对象并供生产器汇总统计 |
| `arrays` | plane 编号、紧凑观测、其余训练字段和来源坐标组成的 NumPy 数组字典 | 承载实际样本，供写盘或解码 |

`EncodedChunk` 是内存中的 Python 对象；`*.npz.zst` 是它序列化、压缩后的磁盘表示。解码得到的六元张量再按训练 `batch_size` 切分，一个 chunk 可以提供多个训练 batch。chunk 大小由预计算时的文件分组决定，与训练 batch 大小相互独立。

当前 `CACHE_SCHEMA_VERSION=1`，固定 `OBS_PLANES=1012`、`OBS_TILES=34`、`ACTION_SPACE=46`，对应 Rust 的 [observation v4](../libriichi/src/consts.rs#L20)。下面按数据转换顺序解读这套格式。

### 10.2 整体执行流程摘要

```text
编码与写盘：
六元 NumPy 样本及来源字段
  -> encode_chunk()
       -> np.asarray()：统一 dtype 和 observation 内存布局
       -> _validate_sample_arrays()：检查形状、有限值、值域和合法动作
       -> np.all()/np.flatnonzero()：划分六类 plane 并记录编号
       -> astype(np.float16).astype(np.float32)：统计量化误差
       -> _pack_bits()/astype()：打包二值数据、量化连续值、收窄整数
       -> EncodedChunk(metadata, arrays)：返回内存编码对象
  -> write_chunk()
       -> json.dumps() + np.frombuffer()：把元数据编码成字节数组
       -> io.BytesIO + np.savez()：生成未压缩 NPZ
       -> zstd.ZstdCompressor(...).compress()：压缩完整 NPZ
       -> file.write()/flush()/os.fsync()/os.replace()：写临时文件并原子替换
       -> os.fsync()：同步父目录
       -> hashlib.sha256()：返回压缩文件摘要及字节数

读取与解码：
.npz.zst
  -> read_chunk()
       -> file.read() + hashlib.sha256()：读取，按需比对预期摘要
       -> zstd.ZstdDecompressor().decompress()：恢复 NPZ
       -> np.load(allow_pickle=False) + json.loads()：读取数组和元数据
       -> 检查 CACHE_SCHEMA_VERSION，返回 EncodedChunk
            ├─ NumPy 验证分支
            │    -> decode_chunk_numpy() + _unpack_numpy()：重构选定行
            │    -> sample_digest()：由验证调用方计算样本摘要
            └─ Torch 设备解码分支
                 -> decode_chunk_torch()
                      -> _torch_rows()：选择行、转换 dtype、传到目标设备
                      -> _unpack_torch()：在目标设备展开 bit
                 -> 返回目标设备上的六元张量

训练组批：
PackedCacheBatchIterator.__init__()
  -> json.load()：读取 manifest；构造方法检查 status
  -> PackedCacheBatchIterator.__iter__()
       -> random.Random(shuffle_seed) + rng.shuffle()：打乱 chunk 列表
       -> 对每个 chunk：
            -> read_chunk()：读取并校验当前文件
            -> rng.shuffle()：打乱当前 chunk 行号
            -> decode_chunk_torch()：恢复整个 chunk
            -> Tensor 切片/torch.cat()：优先补齐已有 carry，再切完整 batch
            -> yield：产出六元 batch；剩余样本留作下一轮 carry
       -> 根据 drop_last 决定是否 yield 最终余量
```

### 10.3 编码与写盘

#### 10.3.1 `encode_chunk()`：统一输入并检查可编码性

[`encode_chunk()`](../mortal/transformer_pipeline/precomputed_cache.py#L139) 先用 `np.asarray()` 统一工作类型：observation 为 float32，mask 为 bool，reward 为 float64，动作、步数、顺位和来源字段为 int64。observation 额外指定 `order='C'`，为后续切片、展平和序列化建立一致的内存布局。

随后 [`_validate_sample_arrays()`](../mortal/transformer_pipeline/precomputed_cache.py#L80) 检查整个 chunk：

- observation 为 `(N, 1012, 34)`，mask 为 `(N, 46)`，其余字段及来源数组为 `(N,)`；
- observation 和 reward 均为有限值，observation 不超出 float16 可表示范围；
- action 位于 `0..45`，并且每行的 `mask[row, action]` 为真；
- 步数、顺位和来源坐标位于后续窄整数类型允许的范围。

这些检查在收窄存储类型前执行，防止越界整数转换时静默回绕。有限值与范围检查也为连续 observation 转为 float16 提供前提；量化误差阈值由第 11.5 节的生产器抽样验证执行。

#### 10.3.2 `np.all()/np.flatnonzero()`：确定 plane 分类

分类针对同一个 plane 在当前 chunk 中的所有样本。对 `obs` 的样本轴和位置轴执行 `np.all(..., axis=(0, 2))`，得到长度为 1012 的判定结果；`np.flatnonzero()` 再提取满足条件的 plane 编号。

编码器先识别全零、全一，再识别每条样本内部的常量 plane，最后处理剩余 plane，形成互斥的六类：

| 类型 | 当前 chunk 内的条件 | 保存方式 |
| --- | --- | --- |
| `zero_planes` | 所有样本、所有位置均为 0 | 只保存 plane 编号 |
| `one_planes` | 所有样本、所有位置均为 1 | 只保存 plane 编号 |
| `constant_binary_planes` | 排除前两类后，每条样本的 34 个位置相同，代表值均为 0/1 | 每样本、每 plane 保存 1 bit |
| `constant_float_planes` | 每条样本的 34 个位置相同，且至少有一个代表值不属于 0/1 | 每样本、每 plane 保存 1 个 float16 |
| `binary_planes` | 至少一条样本沿位置变化，所有值均为 0/1 | 展平 plane 和位置维后 bit-pack |
| `dense_planes` | 剩余 plane | 保存 `(N, plane_count, 34)` float16 |

“逐样本常量”的判定使用 `obs == obs[:, :, :1]`：每条样本与自身第一个位置比较，不要求不同样本的代表值相同。常量 plane 因此只需保存一列，解码时再广播到 34 个位置。

六类编号使用 uint16 保存，并检查总数和去重后数量都等于 1012。编号将紧凑数组与原始通道对应起来；完整分区检查可阻止遗漏或重复回填。由于分类取决于 chunk 中实际出现的值，改变文件分组可能改变压缩率。

#### 10.3.3 `_pack_bits()/astype()`：生成紧凑载荷

分类完成后，编码器提取常量 plane 的代表值，以及普通 plane 的 34 个位置。它先对两类连续数组做 float16 往返，统计误差最大值、绝对值总和及量化值数量。常量连续 plane 每样本只计一个代表值，因此这些统计与解码后完整 observation 的误差平均值口径不同。

[`_pack_bits()`](../mortal/transformer_pipeline/precomputed_cache.py#L67) 把二维 0/1 数组沿第二维按每 8 位存为一个 uint8 字节，调用 `np.packbits(..., bitorder='little')`。这里的 little 表示逻辑上的第一个值占字节最低位。例如：

```text
逻辑位序：[1, 0, 1, 1, 0, 0, 0, 0]
存储字节：1×2^0 + 1×2^2 + 1×2^3 = 13
```

若每行有 M 个有效 bit，编码宽度为 `ceil(M/8)` 字节，末字节不足 8 位时补零。普通二值 plane 先展平为 `(N, plane_count * 34)`，常量二值 plane 为 `(N, plane_count)`；mask 同样打包，所以 46 位只占 6 字节。

连续 observation 通过 `astype(np.float16)` 保存，其他字段采用以下表示：

| 数组 | 存储类型 | 用途 |
| --- | --- | --- |
| `actions` | `uint8` | 动作标签 |
| `mask_bits` | `uint8` packed bytes | 46 维合法动作 mask |
| `steps_to_done` | `uint16` | 有效折扣距离 |
| `rewards` | `float64` | 保留 GRP 奖励精度 |
| `ranks` | `uint8` | 局后顺位 |
| `file_ids` | `uint32` | 源文件列表下标 |
| `player_ids` | `uint8` | 玩家视角 |
| `sample_indices` | `uint16` | 视角内决策位置 |

最后，`encode_chunk()` 将分类编号与载荷放入 `arrays`，将解释信息和统计放入 `metadata`，返回 `EncodedChunk(metadata, arrays)`。其中 `dense_float32_bytes` 仅统计原始 observation，`packed_array_bytes` 统计所有编码数组的原始字节和；两者都不包含 Zstd 压缩结果。

#### 10.3.4 `write_chunk()`：从内存对象生成压缩文件

[`write_chunk()`](../mortal/transformer_pipeline/precomputed_cache.py#L381) 接收编码对象和目标路径。它用 `json.dumps()` 将元数据序列化为 UTF-8 字节，再用 `np.frombuffer(..., dtype=np.uint8)` 把这些字节作为 `__metadata__` 条目交给 `np.savez()`。其余条目来自 `arrays`，由此保持 NPZ 内全部内容都是可安全读取的普通数组。

`io.BytesIO` 接收完整的未压缩 NPZ；`zstd.ZstdCompressor(level=...).compress()` 随后压缩整段字节流。物理层次为：

```text
EncodedChunk(metadata, arrays)
  -> NPZ：__metadata__字节数组 + 各编码数组
  -> Zstd bytes：*.npz.zst的文件内容
```

压缩结果先写到目标文件同目录的临时路径。写入后执行 `flush()` 和文件 `os.fsync()`，再用 `os.replace()` 原子替换目标，最后同步父目录。读者因此不会在目标路径看到只写了一部分的 chunk。生产器负责决定何时将该文件加入索引并发布完整缓存。

函数返回 `serialized_bytes`、`compressed_bytes` 和压缩字节的 SHA256，供生产器写入 chunk 索引。序列化期间完整 NPZ 和压缩结果同时位于内存，内存占用随 chunk 大小增长。

### 10.4 读取与解码

#### 10.4.1 `read_chunk()`：重建编码对象

[`read_chunk()`](../mortal/transformer_pipeline/precomputed_cache.py#L434) 先完整读取压缩文件并计算 SHA256。调用方提供 `expected_sha256` 时会在解压前比对，发现不一致就报错；训练迭代器会传入 manifest 中记录的摘要。

随后，`zstd.ZstdDecompressor().decompress()` 恢复 NPZ 字节，`np.load(..., allow_pickle=False)` 取出普通数组，`json.loads()` 还原 `__metadata__` 中的字典。检查 `schema_version` 后，函数返回与编码端相同结构的 `EncodedChunk`。

这一阶段恢复了紧凑载荷。dense observation 由后续解码器重构；即使只选取少量样本，`read_chunk()` 也已读取并解压整个文件。它没有重新执行编码端的全量业务检查。

#### 10.4.2 `decode_chunk_numpy()`：还原选定行并供验证使用

[`decode_chunk_numpy()`](../mortal/transformer_pipeline/precomputed_cache.py#L259) 根据 `indices` 选定样本及返回顺序；默认值 `None` 表示全 chunk。它先创建全零 `(R, 1012, 34)` float32 数组，R 为选中行数。以下用 P 表示正在恢复的类别所含 plane 数，按顺序执行：

1. 全零 plane 已经就位，全一 plane 按编号填 1。
2. 常量二值通过 [`_unpack_numpy()`](../mortal/transformer_pipeline/precomputed_cache.py#L250) 展开，常量连续值转回 float32；两者从 `(R, P)` 通过末尾单例维广播为 `(R, P, 34)`。
3. 普通二值展开有效的 `P * 34` bit，再 reshape 回三维；普通连续值转回 float32 并填入原通道。
4. mask 展开 46 个有效 bit，其余标量字段恢复训练所需 dtype。

`_unpack_numpy()` 使用与编码端一致的 `bitorder='little'`，通过 `count` 裁掉字节末尾填充位；逻辑宽度为 0 时返回保留样本维的空数组。这样某类 plane 数量为 0 也能沿用同一套回填过程。

返回结果为六元 NumPy 数组，来源字段留在 `chunk.arrays`。验证调用方随后可调用 [`sample_digest(batch, row)`](../mortal/transformer_pipeline/precomputed_cache.py#L460)，按字段顺序把 dtype、shape 和连续数据字节加入 SHA256，用于比较解码样本。这个摘要步骤由生产器的验证流程调用，完整验证机制见第 11.5 节。

#### 10.4.3 `decode_chunk_torch()`：在目标设备重构张量

[`decode_chunk_torch()`](../mortal/transformer_pipeline/precomputed_cache.py#L330) 沿用上述 plane 回填规则，将输出直接分配在指定 Torch 设备上，默认 observation 类型为 float32。这里需要额外处理 CPU 数组到目标设备的转换。

[`_torch_rows()`](../mortal/transformer_pipeline/precomputed_cache.py#L303) 先在 NumPy 中选择行并保证连续布局，再通过 `torch.from_numpy()` 建立 CPU 张量；指定 dtype 时先在 CPU 转换，然后按需锁页并传到目标设备。因此当前连续值默认会在 CPU 由 float16 扩展到 float32 后传输，二值数组仍以 packed bytes 传输。CUDA 锁页路径使用 `non_blocking=True`，允许异步复制；迭代器没有单独预取下一 chunk 的机制。

[`_unpack_torch()`](../mortal/transformer_pipeline/precomputed_cache.py#L320) 在张量所在设备展开 bit：第 k 位取自 `packed[:, k // 8]`，右移 `k % 8` 后与 1 按位相与。这与 NumPy 的有效位顺序相同；解包结果随后 reshape 或广播并写入输出。其余五个字段按相同行号恢复，默认返回：

```text
obs             (R, 1012, 34) float32
actions         (R,)           int64
masks           (R, 46)         bool
steps_to_done   (R,)           int64
rewards         (R,)           float64
ranks           (R,)           int64
```

NumPy 与 Torch 是两套独立的解码实现。发布前的 NumPy 抽样验证未覆盖 Torch 输出的逐值一致性；实际训练选择 Torch 分支，使用这些张量组成 batch。

### 10.5 训练组批

#### 10.5.1 `__init__()`：读取发布清单

[`PackedCacheBatchIterator.__init__()`](../mortal/transformer_pipeline/precomputed_cache.py#L488) 使用 `json.load()` 完整加载 manifest，要求 `status == 'complete'`，并保存 batch size、device、shuffle seed 和 drop_last。此时只读取清单，chunk 文件在开始迭代后打开。缓存总样本数等更完整的检查由外层训练入口执行。

#### 10.5.2 `__iter__()`：按两级随机顺序解码

[`__iter__()`](../mortal/transformer_pipeline/precomputed_cache.py#L501) 创建局部 `random.Random(shuffle_seed)`，复制并打乱 manifest 中的 chunk 列表。进入循环后，先调用 `read_chunk()` 读取当前文件，再用同一个随机数生成器打乱行号，最后把行号传给 `decode_chunk_torch()` 整体解码。

这使 chunk 内部样本随机排列，同时保留 chunk 之间的块级局部性。相同 manifest、seed 和随机算法可以重建顺序；洗牌不会改变进程全局 random 状态。每次调用 `iter(instance)` 都会从头创建这个过程。

#### 10.5.3 `carry`、切片与 `yield`：形成训练 batch

整 chunk 解码完成后，迭代器优先处理上一轮留下的 `carry`，它是六个字段同步保存的未满 batch：

- 当前 chunk 足以补齐时，用头部样本与 carry 执行 `torch.cat()`，立即 `yield` 一个完整 batch，再从已用行之后继续。
- 当前 chunk 仍不足以补齐时，全部并入 carry，继续读取下一个 chunk。一个 batch 因此可能汇集多个小 chunk。
- 没有待补余量后，直接以 Tensor 切片逐个产出完整 batch；最后不足一批的部分成为新的 carry。

第 3.3.2 节的三个 chunk 示例展示了上述过程。全缓存遍历结束后，`drop_last=False` 会产出最终余量，`True` 会舍弃它；中途 chunk 尾部始终参与拼接。

完整 batch 切片与解码张量共享存储，carry 切片也可能继续持有原 chunk 的存储。因此读取器虽然按 chunk 推进，显存峰值仍受整 chunk 大小及存储存活时间影响。产出的每个六元 batch 随后由调用方送入 `train_batch()`。

## 11. `precompute_grp_transformer_cache.py`：生成与发布缓存

### 11.1 用途与输入输出

预计算器读取牌谱及冻结 GRP 权重，复用第 7 章生成六元样本，再调用第 10 章编码、写盘。它还负责输入身份、抽样验证与断点进度。最终产物是压缩 chunk 和可供训练读取的完整 manifest；GRP 推理固定使用 CPU。

缓存生成契约（cache contract）记录“哪些输入、参数和实现产生这份缓存”，恢复时据此判断能否接着写。参数与启动命令见[第 17 章](#run-commands)。

### 11.2 整体执行流程摘要

```text
main() → parse_args()/exclusive_lock() → run()
  -> select_source_files() → load_file_list()：核验完整索引后选择牌谱
  -> build_contract()/source_file_records()：记录输入身份
  -> run()：新建 source_files.json、progress.json，或核对恢复契约和日志
  -> create_sample_generator()：加载一次冻结 GRP，建立 GameplayLoader
  -> 每组源文件：
       collect_file_batch() → iter_file_samples()：收集样本和来源
       -> encode_chunk()/write_chunk()：编码并写 chunk
       -> build_validation_records()/atomic_write_json()：保存抽样记录
       -> append_json_line()：提交 chunks.jsonl 记录
       -> atomic_write_json()：推进 progress.json
  -> read_json_lines()/validate_written_cache()：回读验证全部 chunk
  -> atomic_write_json()：发布 manifest，再把 progress 标记 complete
```

### 11.3 选择文件并固定生成契约

[`select_source_files()`](../mortal/transformer_pipeline/precompute_grp_transformer_cache.py#L142) 先复用完整索引核验，再用局部 `Random(selection_seed)` 打乱文件列表。它跳过已经隔离的路径，选择精确的 `file_count` 份；普通路径缺失或数量不足会报错。选中顺序决定文件编号和 chunk 边界。

[`source_file_records()`](../mortal/transformer_pipeline/precompute_grp_transformer_cache.py#L170) 按此顺序记录路径、字节数和纳秒修改时间。[`build_contract()`](../mortal/transformer_pipeline/precompute_grp_transformer_cache.py#L187) 将记录摘要与以下信息组成契约：

| 字段 | 固定的内容 |
| --- | --- |
| `cache_schema_version`、`observation_version` | 数组格式及观测含义 |
| `selection_seed`、`source_file_count`、`source_files_sha256` | 选择方式、数量和有序源文件身份 |
| `files_per_chunk` | 文件分组，影响分类、压缩及恢复粒度 |
| `compression`、`continuous_dtype`、`reward_dtype` | 压缩算法、级别和数值表示 |
| `pts` | 奖励使用的四个名次效用 |
| `grp_network`、`grp_file`、`grp_sha256` | 奖励模型结构、路径及内容身份 |
| `implementation` | 生成相关 Python 文件和实际导入的 `libriichi` 扩展摘要 |

`sha256_json()` 对规范化 JSON 计算 `contract_sha256`；字典键排序，列表顺序保留。新任务把源文件记录写入 `source_files.json`、游标写入 `progress.json`。恢复任务重新构造当前契约，要求与进度中的摘要相同，并检查 `chunks.jsonl` 的记录数等于 `next_chunk_id`。

完整契约最终进入 manifest，既支持恢复校验，也保留缓存来源。它与训练契约的边界对比如下：

| 契约 | 保存位置 | 主要保护对象 |
| --- | --- | --- |
| 普通离线训练契约 | 普通离线 checkpoint | 文件顺序、训练配置、实现与运行时 |
| 缓存生成契约 | manifest；摘要位于 progress | 六元样本的来源及编码格式 |
| 缓存训练运行契约 | run_config、缓存训练 checkpoint | 已选缓存、初始 checkpoint 和训练配置 |

`gamma`、CQL 权重及优化器参数在训练时使用，未写入缓存生成契约。源码整文件摘要会包含注释变化；身份检查的覆盖限制见第 16 章。

### 11.4 初始化生成器并收集样本

[`create_sample_generator()`](../mortal/transformer_pipeline/precompute_grp_transformer_cache.py#L233) 创建 Transformer 数据集，在主进程显式加载 GRP，再手工建立 `GameplayLoader`。它固定关闭 Oracle 和增强，提取全部玩家；实际遍历由本脚本控制，未经过基类缓冲和自动隔离流程。

[`collect_file_batch()`](../mortal/transformer_pipeline/precompute_grp_transformer_cache.py#L268) 每次将 `files_per_chunk` 个路径交给 Rust 并行解析，然后按输入文件顺序调用 `iter_file_samples()`。六个字段堆叠为 NumPy 数组，另加来源坐标：

```text
file_id    = 源文件在 source_files.json 数组中的下标
player_id  = 玩家视角编号
sample_idx = 该视角中原始决策样本的位置
```

空文件组只推进源文件游标，不生成 chunk。非空组交给 `encode_chunk()` 和 `write_chunk()`，取得编码对象、压缩文件及文件摘要；编码细节沿用第 10 章。

### 11.5 验证、提交与最终发布

压缩文件摘要证明字节与记录一致；样本验证进一步检查编解码是否保留原始训练数据。[`build_validation_records()`](../mortal/transformer_pipeline/precompute_grp_transformer_cache.py#L314) 在原始样本仍在内存时，使用由 `selection_seed + chunk_id` 确定的随机行进行 NumPy 解码：

- action、mask、步数、reward、rank 逐值比较；
- observation 与原始 float32 比较，抽中行的最大绝对误差必须不超过 `5e-4`；
- 保存解码样本摘要、来源坐标和误差统计，供稍后回读。

每个非空 chunk 的提交顺序为：

```text
write_chunk()                      → chunks/chunk_xxxxxx.npz.zst
atomic_write_json()                → validation/chunk_xxxxxx.json
append_json_line() + fsync         → chunks.jsonl 追加一条记录
atomic_write_json()                → progress.json 推进下一文件/下一chunk
```

原始 dense 样本随后释放，磁盘中的抽样记录保留了最终验证所需的信息。该多文件提交可检测日志与游标失配：若中断在最后两步之间，恢复会报错，当前实现不自动修复。单个文件使用原子替换，整个输出目录由同级 `<output-dir>.lock` 排他锁保护。

全部源文件处理完成后，[`validate_written_cache()`](../mortal/transformer_pipeline/precompute_grp_transformer_cache.py#L352) 重新读取每个压缩 chunk，校验文件 SHA256，解码记录指定行，比较六元摘要及来源坐标。只有成功返回后，`run()` 才汇总统计并发布 `status='complete'` 的 manifest，随后更新 progress 完成状态。

这一验证覆盖每个 chunk 的抽样行，使用 NumPy 解码器；它不证明所有行、Torch 解码器或上游 GRP 业务逻辑正确。编码前的形状、有限值和合法动作检查则覆盖全部输入样本。

### 11.6 输出文件与字段速查

文件之间通过 chunk 编号和来源下标关联。普通缓存训练主要消费 manifest 及其列出的压缩文件，其余内容用于生产恢复和审计。

| 文件 | 主要内容 | 使用方式 |
| --- | --- | --- |
| `chunks/*.npz.zst` | `EncodedChunk` 的序列化载荷 | 读取器校验摘要后解码；内层结构见第 10 章 |
| `validation/*.json` | 每个 chunk 的抽样记录数组 | 发布前回读校验、定位样本 |
| `source_files.json` | 有序的 `path/size/mtime_ns` 记录数组 | 数组下标与 `file_id` 对应 |
| `chunks.jsonl` | 每行一条已提交的非空 chunk 记录 | 生产期间追加，恢复时检查数量，完成后嵌入 manifest |
| `progress.json` | 当前契约摘要和下一处理位置 | 预计算 `--resume` 游标 |
| `manifest.json` | 完整契约、统计及 chunk 列表 | 缓存发布入口 |

validation 每条记录包含以下字段：

| 字段 | 含义 |
| --- | --- |
| `chunk_id`、`row` | chunk 编号与内部行号 |
| `digest` | 解码后六元样本摘要 |
| `file_id`、`player_id`、`sample_idx` | 原始牌谱与决策来源 |
| `obs_max_abs_error`、`obs_mean_abs_error` | 该行完整 observation 的误差 |

例如已有缓存的 `validation/chunk_000000.json` 中，`row=758` 对应 `file_id=1, player_id=1, sample_idx=43`，可沿 `source_files.json[1]` 找回牌谱。它索引的是编码前玩家视角中的决策样本，不等于 mjai 文本行号。

chunk 索引及 progress 字段如下：

| 文件 | 字段 | 含义 |
| --- | --- | --- |
| chunks.jsonl | `id/file/validation_file/sha256` | 编号、载荷与验证路径、压缩文件摘要 |
| chunks.jsonl | `file_start/file_count` | 本组在源文件列表中的区间 |
| chunks.jsonl | `sample_start/sample_count` | 生成顺序的累计偏移和样本数 |
| chunks.jsonl | `dense_float32_bytes/packed_array_bytes/serialized_bytes/compressed_bytes` | 原始观测、编码数组、NPZ 及 Zstd 大小 |
| chunks.jsonl | `plane_counts`、`quantized_value_count`、`quantization_abs_sum/max` | 分类与连续值量化统计 |
| chunks.jsonl | `invalid_action_samples` | 该组过滤的非法样本数 |
| progress.json | `status/contract_sha256` | 运行状态与缓存生成身份 |
| progress.json | `next_file_index/next_chunk_id` | 下一文件与下一非空 chunk 编号 |
| progress.json | `total_samples/invalid_action_samples` | 已处理的有效及非法样本计数 |
| progress.json | `started_at/updated_at/completed_at` | 开始、进度更新及完成时间 |

manifest 保存完整 `contract` 及 `contract_sha256`、`source_files_file`、`chunks` 列表，以及文件数、样本数、非法样本数、压缩与量化统计、validation 汇总。`skipped_quarantined_before_selection` 记录选样时遇到并跳过的隔离文件。路径和格式足以让读取器按清单消费固定数据集；大规模索引重复问题集中在第 16 章分析。

## 12. `train_precomputed_cache.py`：消费缓存并恢复训练

### 12.1 用途与输入输出

该入口把完整 manifest 与初始主策略 checkpoint 组合，恢复模型及优化状态，遍历缓存一次。它输出 `latest.pth`、运行契约、训练日志、TensorBoard 和 `epoch_1.completed.json`。供数由 `PackedCacheBatchIterator` 完成，更新使用第 8 章的 `train_batch()`；命令见[第 17 章](#run-commands)。

### 12.2 整体执行流程摘要

```text
main() → parse_args()/exclusive_lock() → run()
  -> load_manifest()：校验完整性；run() 检查初始checkpoint及输出目录
  -> build_run_contract()：固定缓存、起点和训练参数
  -> 新任务 atomic_write_json()/shutil.copy2()；恢复 validate_resume_run_contract()
  -> train_one_epoch()
       -> torch.cuda.set_device()/manual_seed() 等：选择CUDA并固定随机种子
       -> 恢复时 torch.load()/validate_resume_run_contract()：先校验 latest.pth
       -> create_models()：创建组件并加载初始checkpoint
       -> 恢复时 load_state_dict()：用断点状态覆盖，恢复 epoch_progress
       -> PackedCacheBatchIterator：按相同顺序产出batch，跳过已完成部分
       -> train_batch()：更新，累计样本加权指标
       -> SummaryWriter/save_checkpoint()：周期日志与保存
       -> 核对总batch数和样本数，保存最终checkpoint与完成JSON
```

### 12.3 输入与运行契约

[`load_manifest()`](../mortal/transformer_pipeline/train_precomputed_cache.py#L85) 要求 complete 状态、正样本数、非空 chunk 列表，并核对各 chunk 样本数之和。[`run()`](../mortal/transformer_pipeline/train_precomputed_cache.py#L523) 同时要求初始 checkpoint 存在；新任务输出目录必须为空，恢复任务必须有 `latest.pth`。

[`build_run_contract()`](../mortal/transformer_pipeline/train_precomputed_cache.py#L100) 固定 manifest 路径及内容 SHA256、缓存契约摘要、样本/chunk 数、初始 checkpoint 路径及 SHA256、配置路径及完整配置摘要、batch size、shuffle seed、设备和训练器源码摘要。新任务写 `run_config.json`，设置了 `MORTAL_CFG` 时复制为 `source_config.toml`；恢复时 `validate_resume_run_contract()` 核对原契约。

因此，同一个缓存可用于多个新实验，但恢复同一个实验要求起点与运行设置兼容。依赖摘要覆盖不足及迁移条件见第 16 章。

### 12.4 初始化、断点恢复与更新

[`train_one_epoch()`](../mortal/transformer_pipeline/train_precomputed_cache.py#L240) 首先要求可用 CUDA，设置设备、cuDNN 选项及 Python、NumPy、Torch 随机种子，再进入新建或恢复分支。[`create_models()`](../mortal/transformer_pipeline/train_precomputed_cache.py#L150) 调用共享组件构造函数，并严格加载初始 checkpoint 中的三套网络、optimizer、scheduler 和 scaler。

恢复时先检查 `latest.pth` 的专用 schema 与运行契约，然后创建组件、加载初始 checkpoint，最后以断点状态覆盖并恢复 `epoch_progress`。原始 checkpoint 仍用于基准步数与样本计数，因此恢复命令也需要原来的 `--initial-checkpoint`。

迭代器固定 `drop_last=False`。已完成 batch 按 `batches_completed` 跳过，跳过样本数要与断点一致；这些数据仍经过读取、解压和解码，恢复成本随进度增加。新 batch 直接交给 `train_batch()`，返回指标按实际 batch 样本数加权累计。

### 12.5 保存、完成与输出

[`checkpoint_payload()`](../mortal/transformer_pipeline/train_precomputed_cache.py#L174) 定义独立 schema `precomputed-cache-training-v1`，保存三套网络、优化状态、基准 checkpoint 信息、运行契约和 epoch 进度。全局 `steps/samples_seen` 由初始值加本次完成量计算；`save_checkpoint()` 复用原子写入。

周期日志通过 SummaryWriter 记录指标及吞吐，周期保存写入 `latest.pth`。捕获到异常且已完成至少一个 batch 时会尝试保存中断状态；强制终止等无法执行异常处理的情况只能依靠上次成功 checkpoint。

缓存全部读完后，检查完成 batch 数等于 `ceil(sample_count/batch_size)`、完成样本数等于 manifest 总数。保存最终 checkpoint 并计算 SHA256 后，再写完成 JSON。

| 输出 | 内容 |
| --- | --- |
| `latest.pth` | 可恢复的模型、优化器及 epoch 进度 |
| `run_config.json` | 运行契约、摘要和配置快照 |
| `source_config.toml` | 设置 `MORTAL_CFG` 时复制的原配置 |
| `train.log`、`tensorboard/` | 指标、吞吐、时间和资源记录 |
| `epoch_1.completed.json` | 完成样本/batch 数、计时、最终指标、checkpoint 路径和摘要 |

该脚本每次只安排一次 manifest 遍历，没有多 epoch 外层循环。专用 batch 进度也不能直接交给普通文件分片训练器恢复。

## 13. `benchmark_offline_grp_transformer_bs1024.py`：测量传统供数

### 13.1 用途与输入输出

该脚本读取一批真实牌谱，比较 DataLoader worker、文件批次和 Rayon 线程组合，输出供数吞吐与主机资源统计。它不调用 `train_batch()`；所得数值衡量传统数据准备能力。命令见[第 17 章](#run-commands)。

### 13.2 整体执行流程摘要

```text
main() → parse_args()
  -> load_file_list()/random.Random.shuffle()：选择测量文件
  -> 对每个候选 benchmark_candidate()
       -> create_data_loader()：设置worker、文件批次与Rayon线程
       -> next(iterator)：预热
       -> cpu_snapshot()/read_meminfo()/process_rss()：计时与采样
       -> 消费测量batch；计时结束后继续耗尽iterator
       -> 返回供数与资源统计
  -> json.dumps()/print()：输出候选结果
```

### 13.3 选样与候选配置

[`main()`](../mortal/transformer_pipeline/benchmark_offline_grp_transformer_bs1024.py#L116) 将进程内 GRP 路径指向源权重，核验完整索引，再按 epoch seed 打乱并截取 `--files` 份牌谱。[`benchmark_candidate()`](../mortal/transformer_pipeline/benchmark_offline_grp_transformer_bs1024.py#L47) 逐个建立以下候选：

| 候选 | workers | 每批源文件 | 每 worker 的 Rayon 线程 |
| --- | ---: | ---: | ---: |
| A | 2 | 6 | 6 |
| B | 3 | 4 | 4 |
| C | 4 | 3 | 3 |

若已测 B 且其可用内存低于 4 GiB，则跳过 C。多 worker 沿用 `spawn` 配置，当前进程环境中的线程设置会传入新 worker。

### 13.4 计时与结果含义

消费预热 batch 后开始计时。`cpu_snapshot()` 读取系统 CPU 计数，`read_meminfo()` 读取主机可用内存和 swap，`process_rss()` 汇总 worker RSS；这些统计的范围不同，应按字段解释。

达到测量 batch 数后冻结计时和统计，但循环仍继续读取所选文件直到耗尽。返回的 `samples_per_second` 是测量窗口的供数速度，不包含主模型更新。它可与缓存供数指标一起分析瓶颈；要计算端到端训练加速，应另外取得相同条件下包含 `train_batch()` 的传统训练吞吐。

## 14. `benchmark_precomputed_cache.py`：分解缓存性能

### 14.1 用途与输入输出

该脚本分别测量 CPU 解码、GPU 供数和缓存端到端训练，输入为完整 manifest 及可选主策略 checkpoint，输出 JSON 结果。训练测量会更新内存中的模型和优化器，结果不写回 checkpoint。启动与跳过选项见[第 17 章](#run-commands)。

### 14.2 整体执行流程摘要

```text
main() → parse_args()/load_manifest()
  -> 可选 benchmark_cpu_decode()
       -> read_chunk()/decode_chunk_numpy()：读取解码并检查动作合法性
  -> 可选 benchmark_gpu_supply()
       -> read_chunk()/decode_chunk_torch() → torch.cuda.synchronize()
  -> 可选 benchmark_cached_training()
       -> load_training_state()：创建并恢复组件
       -> PackedCacheBatchIterator → train_batch()：预热后计时
       -> 需要时更换epoch seed再次遍历，最终 torch.cuda.synchronize()
  -> 计算比率与空间估算，json.dumps()/print()；可选写 --output
```

### 14.3 清单读取与两种供数测量

[`load_manifest()`](../mortal/transformer_pipeline/benchmark_precomputed_cache.py#L24) 检查 complete 状态，并为供数测量截取 `--max-chunks` 指定的列表。CPU 分支 [`benchmark_cpu_decode()`](../mortal/transformer_pipeline/benchmark_precomputed_cache.py#L34) 计入文件读取、SHA256、Zstd 解压、完整 NumPy 重构及动作合法性检查。

[`benchmark_gpu_supply()`](../mortal/transformer_pipeline/benchmark_precomputed_cache.py#L54) 计入读取、解压、设备传输和 Torch 重构；最终 CUDA 同步确保计时覆盖已提交的 GPU 工作，并记录 allocated/reserved 峰值。两个供数分支都不执行主模型更新。

### 14.4 训练测量与输出解释

[`benchmark_cached_training()`](../mortal/transformer_pipeline/benchmark_precomputed_cache.py#L100) 通过 `load_training_state()` 恢复三套模型及优化状态，再用完整 manifest 构造迭代器。`--max-chunks` 不限制这一分支。默认先预热 5 步，再测 250 步，batch size 为 1024；`drop_last=True` 丢弃尾批，步数不够时以新 epoch seed 继续遍历。

`training_speedup` 的实际计算为“缓存训练吞吐 ÷ `--baseline-samples-per-second`”，分母默认 3260。这个参数没有自动关联传统测试；只有分母来自同条件端到端训练时，比率才具有训练加速含义。使用第 13 章的纯供数结果作为分母，会混合两种口径。

空间估算使用硬编码的 `ESTIMATED_FULL_DATASET_SAMPLES=838885333` 乘以 manifest 中每样本压缩字节。它是外推值，实际结果及其边界见第 15 章。

### 15.3 外推范围

按每样本 502.32 bytes 与基准脚本估计的 838,885,333 条全量样本相乘，得到约 392.45 GiB 缓存空间。此值依赖样本总量估计及 10k 子集的压缩分布；全量牌谱长度、分类和 I/O 局部性可能不同。

10k 缓存训练一遍与全量牌谱训练一遍的样本暴露量不同。判断训练加速需同范围、同模型及计时口径的端到端对照；判断策略质量还需相同评测协议。正文保留这组历史结果作为规模参考。

## 16. 当前限制与扩展方向

### 16.1 格式、数值与供数

| 当前实现 | 含义或扩展方向 |
| --- | --- |
| schema v1 固定 `(1012, 34)` 和 46 个动作 | 对其他观测版本需另行适配格式 |
| 连续观测使用 float16，验证采用抽样 | 允许有限量化误差，不能由抽样推出所有解码路径正确 |
| chunk 级和 chunk 内洗牌 | 保留局部性，输入顺序与传统 DataLoader 不同 |
| 整 chunk 解码，切片可能持有整块存储 | 控制 chunk 大小时需同时考虑压缩率和显存 |
| 无显式下一 chunk 预取 | 后续可评估 I/O、CPU 解压与训练重叠，需单独验证收益 |

### 16.2 身份、恢复与验证边界

第 11 章描述的是已有检查机制，其覆盖范围存在以下限制：

- 源牌谱身份采用路径、大小和 mtime；保持这些元数据的内容改动可能逃过检查。更强保证可使用文件内容摘要。
- 源文件记录在启动时构造；发布前没有再次生成源数据身份，也未回读核验 `source_files.json`。单独修改审计文件可能破坏 `file_id` 到路径的映射。
- 缓存生成契约记录整份 Python 文件及扩展摘要，纯注释变化也阻止旧任务恢复；导入的 `load_file_list()` 所在训练器没有被直接列入实现摘要。
- `validation-samples-per-chunk` 和 Rayon 线程数没有进入缓存生成契约；前者变化可能让一次恢复前后的抽样策略不同。
- 数据损坏会中止预计算；chunk 日志与 progress 在提交窗口中断时可能失配，当前实现不自动协调。
- 验证 JSON 没有独立摘要写入 manifest。发布前会回读，普通训练不再读取这些 JSON；NumPy 验证也未逐值覆盖 Torch 实现。

第 12 章的缓存训练运行契约仅记录训练器自身源码摘要，没有直接记录当前解码器、共享 `train_batch()` 实现和完整运行时。因此恢复检查并未穷尽所有语义变化。可将这些依赖统一纳入消费者实现清单。

缓存训练只安排一次 manifest 遍历；恢复需要从头读取和解码后跳过已完成 batch。后续可记录可重建的 chunk/行游标以减少重放，但必须同时处理跨 chunk 余量和随机状态。

目录迁移例外由 `_bootstrap.py` 的精确旧/新摘要白名单限定，适用于训练断点。预计算生成契约没有同样的迁移例外。已完成缓存的读取按 schema 和 chunk 摘要进行，不会重算历史生产源码契约。

### 16.3 manifest 内嵌索引的规模取舍

manifest 复制完整 `chunks.jsonl` 记录，使消费者取得单一发布快照；原子写入后即可固定 chunk 集合。其代价是磁盘重复和 `json.load()` 的对象开销。

| 现有 10k 缓存元数据 | 字节数 |
| --- | ---: |
| `chunks.jsonl` | 1,153,996 |
| `manifest.json` | 1,437,999 |
| manifest 占 chunk 压缩数据 | 约 0.044% |

对当前实验，磁盘成本很小。按 1,277,548 份文件、每 chunk 六份估算，非空分组可达约 212,925 个；沿用现有记录体积，manifest 约 175 MiB。解析后的大量 Python 字典还会增加内存，训练入口和迭代器各自加载时也可能保留多份对象。该估算未测量全量峰值 RSS。

一个可选扩展是让 manifest 引用完成后的索引文件：

```json
{
  "status": "complete",
  "chunk_index": {
    "file": "chunks.jsonl",
    "sha256": "...",
    "count": 212925
  }
}
```

这是待实现的结构示意。完成索引后计算摘要，再发布小 manifest，可以消除重复嵌入；仅把记录移出 manifest 仍不能消除“完整解析所有记录”的内存成本。训练必需索引还可收窄为 `id/file/sha256/sample_count`，审计统计另存，进一步考虑紧凑二进制索引。

同规模还会生成约 21 万个 validation 小文件，可考虑分片 JSONL 或压缩审计文件。上述方向属于后续设计，当前格式和读取器均未实现。
